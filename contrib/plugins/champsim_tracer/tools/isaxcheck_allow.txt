# isaxcheck allowlist — justified residual decoder-metadata disagreements.
#
# Author: Maccoy Merrell
# SPDX-License-Identifier: GPL-2.0-or-later
#
# isaxcheck compares the decode metadata the ChampSim Tracer actually
# consumes (cap_disas_raw_detail() from disas/capstone.c — Capstone plus
# every correction the boundary applies) against the LLVM MC layer, over an
# exhaustive sweep of the opcode-bearing encoding space.  Anything it reports
# that is not listed here fails the gate.
#
# Format:  <isa> <signature key>
#          `#` starts a comment; `*` in the key is a glob wildcard.
# Signature keys are `CLASS mnemonic [qualifier]`, where the qualifier for
# the register classes is the difference set with register numbers collapsed
# to `#` (so `+r#` means "some general-purpose register", `+za` means "the
# SME accumulator tile").
#
# EVERY ENTRY BELOW NAMES: what the disagreement is, why it is not a tracer
# defect, and how to check whether it can be deleted.  An entry that cannot
# carry those three things is a bug to fix, not a line to add here.
#
# Observed against Capstone 6.0.0-Alpha7 (subprojects/capstone.wrap) and
# LLVM 18 MC.  On a Capstone bump: rebuild, re-run
# `python -m champsim_tracer_validator full`, and delete every entry whose
# signature no longer appears.  `capstone_workaround_probe` answers the
# complementary question — whether an existing disas/capstone.c workaround
# has become unnecessary.

# =====================================================================
# 1. Where LLVM is the one that is wrong, or models something that is not
#    architectural.  These are not Capstone defects and never will be
#    "fixed"; they are removable only if LLVM's own descriptions change.
# =====================================================================

# LLVM's MIPS BC1T/BC1F/BC1TL/BC1FL carry `Defs = [AT]`, an ASSEMBLER-MACRO
# artifact: the assembler may expand a long-range FP branch through $at, so
# the pseudo-instruction claims to clobber it.  A branch writes no GPR at
# all.  Capstone inherited the same claim through the TableGen sync, and
# disas/capstone.c now removes it (see the FP condition-code workaround) —
# which is exactly why this shows up as "Capstone is missing a write".
# Keeping the phantom would fabricate a WAW hazard on $at across every FP
# branch.  Removable when LLVM stops modelling the macro expansion in
# MCInstrDesc, which is not expected.
mipsel R-wr-missing bc1* +r#

# LLVM's MIPS BGEZAL / BLTZAL / *ALL describe the tested register as an
# operand of the pseudo rather than a use, so it reports no reads at all.
# Capstone (and the architecture) are right: the branch reads the register
# it compares against zero.
mipsel R-rd-phantom b*zal* +r#

# LLVM's MIPS JR / JALR pseudos likewise omit the target register read.
mipsel R-rd-phantom jr +r#
mipsel R-rd-phantom jalr +r#
mipsel B-ret-mismatch jr cs-ret

# (LWL/LWR read their own destination — the partial-merge workaround in
# disas/capstone.c supplies it, LLVM models the merge as a tied operand on
# the *store* side only.  Covered by the explicit `lwl` / `lwr` entries in
# section 3; the class-wide form that used to live here spelled the family
# `lw[lr]`, which the matcher reads literally — `*` is its only wildcard —
# so it never matched anything.)

# LLVM gives every SSE/AVX-class RISC-V FP vector op `Uses = [FRM]` but, in
# LLVM 18, drops the `[VL, VTYPE]` the base class supplies — so the FP
# vector ops claim not to depend on the vector configuration that decides
# how many elements they process.  Architecturally they do, and
# disas/capstone.c supplies the reads (see the RVV vector-configuration
# workaround).  Removable when LLVM's RISCVInstrInfoV* descriptions carry
# VL/VTYPE on the FP forms; re-check by running this sweep against a newer
# llvm-config.
riscv64 R-rd-phantom vf* +vl,vtype
riscv64 R-rd-phantom vl*.v +vl,vtype
riscv64 R-rd-phantom vs*.v +vl,vtype

# The RVV unconditionally-masked carry/merge families (`.vvm` / `.vxm` /
# `.vim` / `.vfm`) take v0 as a mandatory DATA operand: the carry-in of
# vadc/vmadc, the borrow-in of vsbc/vmsbc, the select control of
# vmerge/vfmerge.  RVV v1.0 §11.4, §11.5 and §11.15 all define it as read.
# BOTH decoders print `v0` in the operand string and NEITHER reports the
# read, so this is the one disagreement class this tool could never have
# discovered — it was fixed from the specification (see the v0 restore in
# cap_fill_generic_operands) and carries its own regression check,
# probe_rv_v0_carry_mask, precisely because the sweep cannot cover it.
# Without the read a multiword add chain's carry serialisation vanishes.
# The unmasked siblings (`vmadc.vv`, `vmsbc.vx`) genuinely do not read v0
# and are deliberately not matched.  Removable when LLVM's
# RISCVInstrInfoV descriptions mark the V0 operand a use.
riscv64 R-rd-phantom vadc.v*m +v#
riscv64 R-rd-phantom vmadc.v*m +v#
riscv64 R-rd-phantom vsbc.v*m +v#
riscv64 R-rd-phantom vmsbc.v*m +v#
riscv64 R-rd-phantom vmerge.v*m +v#
riscv64 R-rd-phantom vfmerge.v*m +v#

# LLVM adds an ABI-modelling implicit SP use to call instructions.  It is
# not an architectural read; the tool already suppresses it for the plain
# call forms, but not for the pointer-authenticated ones, which LLVM
# classifies differently.
aarch64 R-rd-missing bl* +sp

# LLVM gives AArch64 MRS/MSR an NZCV def that the architecture does not.
aarch64 R-wr-missing mrs +nzcv
aarch64 R-wr-missing msr +nzcv

# The TLBI operations that take NO Xt argument (TLBI VMALLE1, VMALLS12E1IS,
# ALLE2, …) are still encoded in the SYS format, which has an Rt field; the
# architecture requires that field to be 0b11111 for them.  LLVM keeps the
# syntactic operand and reports it read whatever it holds, so an encoding
# that puts a real register number in an Rt the operation does not use looks
# like a lost read.  Capstone is right — the operation reads no register —
# and the disagreement exists only on reserved encodings no assembler emits
# (`tlbi vmalls12e1is` written properly names XZR, which folds away).  The
# argument-taking forms (`tlbi vae2is, x0`) agree on both sides.  Newly
# reachable since the sweep started filling Rn=30 (see sweep_aarch64).
aarch64 R-rd-missing tlbi +r#

# =====================================================================
# 2. Deliberate tracer modelling decisions.  The disagreement is real but
#    the tracer's answer is the intended one, so "fixing" it would be a
#    regression.  Removable only if the modelling decision changes.
# =====================================================================

# Memory-hint and cache-maintenance instructions (AArch64 PRF*, MIPS
# PREF/PREFE/CACHE/CACHEE/SYNCI) emit no TCG memop.  The tracer classifies
# them as GEN_OP_PREFETCH / GEN_OP_CACHE_FLUSH and synthesises the address
# slot from the opcode class, so the boundary deliberately leaves their MEM
# operand's access bits empty rather than minting a load lane that no
# memory callback will ever fill — see cap_aarch64_infer_mem_access(), which
# returns 0 for the prefetch classes on purpose, and the GEN_OP_PREFETCH
# comment in champsim_tracer_generic_ids.h.  LLVM reports mayLoad.
aarch64 Z-access0 prf* MEM
aarch64 M-miss-load prf*
mipsel Z-access0 pref* MEM
mipsel Z-access0 cache* MEM
mipsel Z-access0 synci MEM
mipsel M-cs-mem-llvm-none pref*
mipsel M-cs-mem-llvm-none cache*
mipsel M-cs-mem-llvm-none synci

# SVE vector ADR computes an address without accessing memory — the AArch64
# equivalent of x86 LEA.  An access-free MEM operand is the correct
# representation and the operand walker skips it for exactly that reason
# ("LEA / prefetch-hint MEM operands lack both READ and WRITE — no real
# memop, don't count", champsim_tracer_decode.cc).
aarch64 Z-access0 adr MEM
aarch64 M-cs-mem-llvm-none adr

# =====================================================================
# 3. Feature sets the tracer does not model.  These are honest gaps with a
#    named boundary, documented in docs/limitations.rst.
# =====================================================================

# SME.  The ZA matrix accumulator and its tile/slice operands arrive as
# Capstone AARCH64_OP_SME operands, for which the plugin operand ABI has no
# representation (there is one register slot per operand and an SME operand
# names a tile, a slice-select GPR and an immediate index).  Every SME
# instruction therefore loses its accumulator dependency.  The tracer does
# not target SME workloads and QEMU's SME support is itself partial.
# Closing this needs an operand-ABI extension, not a boundary fix.
# (was a class-wide rule; narrowed to explicit signatures so a NEW
#  unmodelled operand type on AArch64 still fails the gate)
#  the complementary `R-*-phantom * +za*` form is deliberately absent: the
#  boundary drops SME operands, so a ZA register can only ever be MISSING
#  from its sets, never phantom in them.)

# SVE2.1 / SME2 predicate-as-counter PAIR destinations: `whilege
# { p14.b, p15.b }, ...` writes two predicate registers and Capstone reports
# only the first.  Single-predicate WHILE* forms — which is what any SVE
# (as opposed to SME2) workload emits — are correct, and are verified by the
# predicate end-to-end test.  Re-check on a Capstone bump with
# `cstool -d arm64 ff5f2025`.
aarch64 R-wr-missing while* +p#
aarch64 R-wr-missing p*ext* +p#
aarch64 R-wr-missing pext +p#
aarch64 R-rd-missing psel +r#

# RISC-V CSR operands.  Capstone types the CSR-number operand as one the
# boundary cannot map to a register, so a CSR access shows no CSR
# dependency.  The tracer models CSRs only through the specific ones the ISA
# tables name (frm/fflags -> REG_FCSR, vl/vtype -> REG_VCTRL); a general CSR
# index has no generic register id.  Documented in docs/limitations.rst.

# MIPS MSA and FP control-register banks: MSAIR / MSACSR / MSASave /
# MSAModify and the low-numbered FP control registers are named by Capstone
# as bare coprocessor indices.  The tracer folds every coprocessor register
# onto REG_SYS and every FP control register onto REG_FCSR, so the bank
# distinction is not expressible in the dependency model even when the
# decoders agree on it.  Note this is NOT the "coprocessor writes
# attributed to a same-numbered GPR" family the ground-truth study
# reported: at the boundary those registers arrive as MIPS_REG_COP0n /
# MIPS_REG_COP2n and map correctly (verified with
# `cstool -d mips32r2 00188040`, `mtc0 $zero,$3`).
mipsel R-rd-missing c*cmsa +msa*
mipsel R-rd-phantom c*cmsa +cop#
# (The ten `*c2` coprocessor-register entries that used to open this block
# were an artifact of this tool, not a disagreement.  Its MIPS normaliser
# dropped the coprocessor index by keeping only the LAST digit, so COP2
# register 15 -- LLVM's `COP215` -- read as `cop5` and compared against the
# wrong register for every coprocessor register above 9.  The index comes
# off the front now.  The blind spot that hid it is the same one the sweep
# fill sets exist to close: Rd never took a value large enough to reach a
# two-digit coprocessor register until (31, 0) was added to the MIPS fills.)
mipsel R-rd-missing cfc1 +fcsr
mipsel R-rd-phantom cfc1 +cop#
mipsel R-wr-missing ctc1 +fcsr
mipsel R-wr-phantom ctc1 +cop#
mipsel R-rd-missing mthc1 +f#

# (MIPS DSP accumulators $ac1..$ac3 on the two-operand MADD/MSUB forms:
# Capstone names only the implicit HI:LO pair.  The tracer's HI:LO chain is
# intact (probe_implicit_acc pins it); the extra DSP accumulators are not.
# Covered by the explicit madd / maddu / msub / msubu entries in section 3;
# the class-wide form that used to live here spelled the family
# `m[as][du][db]*`, which the matcher reads literally and never matched.)

# =====================================================================
# 4. The subtarget gap (class D-cs-only): the boundary decoded it and
#    LLVM did not.
#
#    THIS CLASS IS SPECIAL AND THE TOOL ENFORCES IT.  A `D-cs-only`
#    signature is not one finding among many — it is an encoding on which
#    the register, memory and branch comparisons DO NOT RUN AT ALL, because
#    a rejected LLVM decode short-circuits the compare.  The number of
#    signatures here is therefore the size of this gate's blind spot, and
#    isaxcheck reports it as `subtarget_gap=<signatures>/<encodings>` in
#    its summary line.
#
#    Two rules follow, and isaxcheck refuses an allowlist that breaks the
#    first of them:
#
#      * NO WILDCARDS.  `aarch64 D-cs-only *` was one line, and it hid
#        every extension family a Capstone bump might add.  Each signature
#        is named, or the entry is refused at load time.
#      * A LINE HERE IS THE SECOND-CHOICE FIX.  The first choice is to add
#        the missing feature to kIsaTable so the gap CLOSES.  That is what
#        happened to mipsel (+mips3d) and to the whole of riscv64, which
#        now reports subtarget_gap=0/0 — and closing the RISC-V gap is what
#        made the Zacas `amocas.*` dropped destination visible at all.
#
#    So the only entries below are AArch64's, where `+all` is already the
#    widest subtarget LLVM has and the residue is Capstone accepting
#    encodings the architecture does not define.  See also
#    docs/limitations.rst, "Wrong-path decode of arbitrary bytes".
# =====================================================================

# (a) Architecturally-fixed fields holding reserved values.  `0x88c0e022`
# has Rs != 0b11111 and is therefore not a valid LDAR, but Capstone decodes
# it as `ldar w2, [x1]` while LLVM rejects it.  The same shape covers the
# load/store-exclusive and acquire/release families (Rs and Rt2 must both
# read 0b11111), ADDG/SUBG (op3 must be 0b00) and SB (CRm must be 0b0000).
# On the correct path the bytes never occur.  On the wrong path, where the
# tracer decodes arbitrary bytes, it means a template can describe a
# plausible instruction where the hardware would raise UNDEFINED; the
# tracer's wrong-path fidelity contract already treats wrong-path
# instruction identity as best-effort.
# Verify with `cstool -d arm64 22e0c088` on a Capstone bump: if Capstone
# starts rejecting the reserved encodings, every line here goes dead and
# the tool says so.
aarch64 D-cs-only addg
aarch64 D-cs-only ldar
aarch64 D-cs-only ldarb
aarch64 D-cs-only ldarh
aarch64 D-cs-only ldaxr
aarch64 D-cs-only ldaxrb
aarch64 D-cs-only ldaxrh
aarch64 D-cs-only ldlar
aarch64 D-cs-only ldlarb
aarch64 D-cs-only ldlarh
aarch64 D-cs-only ldxr
aarch64 D-cs-only ldxrb
aarch64 D-cs-only ldxrh
aarch64 D-cs-only sb
aarch64 D-cs-only stllr
aarch64 D-cs-only stllrb
aarch64 D-cs-only stllrh
aarch64 D-cs-only stlr
aarch64 D-cs-only stlrb
aarch64 D-cs-only stlrh
aarch64 D-cs-only subg

# (b) CONSTRAINED UNPREDICTABLE register aliasing on the pair forms.  The
# architecture leaves `ldp w2, w2, [x1], #28` (Rt == Rt2) and
# `stp wzr, w0, [x0], #40` (writeback Rn == Rt2) undefined; LLVM refuses
# them, Capstone decodes them.  This is the same best-effort wrong-path
# space as (a) — the difference is that the fields are legal in isolation
# and only their COMBINATION is not, so no field check would catch it.
aarch64 D-cs-only ldaxp
aarch64 D-cs-only ldnp
aarch64 D-cs-only ldp
aarch64 D-cs-only ldpsw
aarch64 D-cs-only ldxp
aarch64 D-cs-only stgp
aarch64 D-cs-only stp

# 4b. Residual class-R/Z findings on the RISC-V space the closed subtarget
#     gap made visible.  These were inside "LLVM rejects this" until the
#     kIsaTable feature list was completed; none of them is reachable by a
#     binary the tracer traces today, and each names its fix.

# Zacas compare-and-swap: `amocas.d t0, s2, (t1)` has rd tied — it is the
# comparand on the way in and the loaded value on the way out — and
# Capstone reports it READ-only, so the destination is dropped ENTIRELY
# (csWR{} against llvmWR{r5}).  This is the same Capstone tied-operand
# handling that loses the RVV multiply-accumulate destination, which
# disas/capstone.c already repairs; the Zacas family needs the same
# treatment there.  Not reachable yet: it takes -march=...\_zacas to emit
# one.  FIX: extend the RISC-V tied-destination repair in
# cap_fill_generic_operands() to the amocas.* forms; delete these lines
# when it lands.
riscv64 R-wr-missing amocas.d +r#
riscv64 R-wr-missing amocas.d.aq +r#
riscv64 R-wr-missing amocas.d.aqrl +r#
riscv64 R-wr-missing amocas.d.rl +r#
riscv64 R-wr-missing amocas.w +r#
riscv64 R-wr-missing amocas.w.aq +r#
riscv64 R-wr-missing amocas.w.aqrl +r#
riscv64 R-wr-missing amocas.w.rl +r#

# CORE-V (XCVmac) `cv.*nr` accumulate-and-round forms: identical shape to
# the Zacas case above — a tied destination Capstone reports read-only.
# A vendor extension; QEMU implements no CORE-V core, so no trace can ever
# contain one.  MODELLING DECISION: not worth a boundary workaround on its
# own; it would fall out of a general tied-destination repair.
riscv64 R-wr-missing cv.addnr +r#
riscv64 R-wr-missing cv.addrnr +r#
riscv64 R-wr-missing cv.addunr +r#
riscv64 R-wr-missing cv.addurnr +r#
riscv64 R-wr-missing cv.subnr +r#
riscv64 R-wr-missing cv.subrnr +r#
riscv64 R-wr-missing cv.subunr +r#
riscv64 R-wr-missing cv.suburnr +r#

# XVentanaCondOps `vt.maskc` / `vt.maskcn` are SCALAR conditional moves
# whose mnemonic happens to begin "vt."; Capstone files them with the
# vector forms and attaches the RVV context reads (vl, vtype) that every
# real vector instruction has.  Phantom dependencies on a vendor extension
# QEMU does not implement.  WONT-FIX at the boundary: the fix belongs in
# Capstone's own instruction description, and a name-based exclusion here
# would be a second guess at the same table.
riscv64 R-rd-phantom vt.maskc +vl,vtype
riscv64 R-rd-phantom vt.maskcn +vl,vtype

# Zfa `fli.s/d/h` load an immediate from a 32-entry constant table, and
# Capstone types that operand RISCV_OP_FP — a type the boundary's RISC-V
# operand filler has no case for, so it lands in QEMU_PLUGIN_OP_INVALID and
# the instruction's immediate is lost.  The register sets agree, so no
# dependency edge is wrong; what is missing is the constant.  Same class as
# the RISC-V CSR operands in section 2.  FIX: a RISCV_OP_FP case in
# cap_fill_generic_operands() alongside RISCV_OP_IMM.
riscv64 Z-unmodelled-op fli.d
riscv64 Z-unmodelled-op fli.h
riscv64 Z-unmodelled-op fli.s

# RVV whole-register MOVE reports the vector-context CSRs it does not read.
# `vmv2r.v` copies a register GROUP by architecture, independent of vl and
# vtype -- that is the point of the instruction -- and Capstone attaches the
# RVV context reads anyway.  Same family as the vl/vtype phantoms above, and
# reached only once (1, 0) joined the RISC-V sweep fills: the whole-register
# moves need rd = v0 to print their two-operand form.
riscv64 R-rd-phantom vmv2r.v +vl,vtype

riscv64 R-wr-missing cmop.* +r#
riscv64 R-rd-missing *ntl* +r#

# RISC-V hint encodings whose architectural effect is "nothing":
# `c.addi rd, 0`, `c.slli64`, `c.srai64`, `c.srli64` are HINTs.  Capstone
# reports no write (correct for a hint); LLVM reports the nominal write.
riscv64 R-wr-missing c.* +r#

# RISC-V JAL/JALR link-register write: the alias-hidden link dataflow is
# recovered inside the plugin by probe_rv_link_dataflow (verified
# end-to-end: `call $0x105cc -> %lr`), which is downstream of the boundary
# this tool measures.  The trace is correct; the boundary alone is not.
riscv64 R-wr-missing jal +r#
riscv64 R-wr-missing jalr +r#
riscv64 R-rd-phantom jalr +r#

# --- x86_64 baseline.
#
# x86 is swept for REGRESSION detection only, and its residual is recorded
# here wholesale rather than triaged signature by signature.  The reason is
# that x86 already has an independent, DYNAMIC ground truth that this static
# check cannot match: the Intel PIN pairing, which found the five defects the
# existing disas/capstone.c x86 workarounds address and which remains the
# authority for effective addresses, real access sizes, rep fan-out and
# segment interactions.  Against LLVM MC the x86 residual is dominated by
# four systematic modelling differences that describe no defect —
# prefix-consumption disagreements (Capstone folds `64 65` into one
# instruction, LLVM stops at `gs`), `bnd` versus `repne` prefix printing,
# LLVM's shadow-stack and flag-modelling artifacts, and AT&T operand-order
# effects.  A handful of entries here ARE candidate defects worth their own
# arc (`adox` losing its destination read, `bswapw`, `cmpxchg8b`/`16b`
# losing mayStore, `cldemote`); they are tracked as x86 work, not as part of
# the non-x86 decode-metadata arc this gate was built for.
#
# What this block still buys: a Capstone bump that changes ANY x86 signature
# shows up as a gate failure rather than as silent trace corruption.

# 6. The x86 group-opcode and x87 space, reached once ModRM.reg was swept.
#
#    ModRM.reg is not a register on the group opcodes -- 0x80/0x81/0x83,
#    0xC0/0xC1/0xD0-0xD3, 0xF6/0xF7, 0xFE/0xFF and most of the 0x0F groups
#    -- it is an OPCODE EXTENSION.  Two fixed ModRM tails reached two of its

#    independent ground truth remains the PIN pairing, and this sweep is
#    regression detection.
# =====================================================================

# 7. The control state the boundary started reporting, that LLVM does
#    not describe.
#
#    Three repairs landed after this file was last derived -- the AArch64
#    system-register operand, the RISC-V CSR operand, and the FPCR/NZCV
#    implicit reads -- and they moved the disagreement to the other side.
#    Where the boundary used to drop a register and LLVM named it, the
#    boundary now names state LLVM's MCInstrDesc carries no implicit use
#    for at all.  A `phantom` verdict in this section does NOT mean the
#    tracer invented a dependency: it means the second decoder has no
#    description of that state, the same way it has none for x86 MXCSR
#    (section 1).  Where the two disagree about architectural fact rather
#    than about modelling, the instrument that decides is the
#    implicit-operand table, whose ground truth is the Arm MRA and the
#    Sail model rather than a decoder -- and it now scores these rows OK.
#
#    The system-register TOKEN in these keys is the class the dependency
#    model records (`sys`, `fcsr`, `vctrl`, `vstart`), not the
#    architectural name.  The tracer folds the whole system-register space
#    onto REG_SYS apart from the few it models specifically, so a token per
#    architectural register would key a separate signature for each -- 11445
#    of them on RISC-V, one allowlist line per CSR number.  WHICH system
#    register an instruction touches is a real question and it is the
#    implicit table's, which names each one exactly.
# =====================================================================
