# isaxcheck fields-layer allowlist — the justified residual of
# `isaxcheck --layer=fields --classes=MBR`, which compares the InsnFields
# the dependency model records (what the trace is BUILT from) against
# LLVM MC.  Same file format and matching rules as isaxcheck_allow.txt;
# a separate file because the allowlist loader is layer-blind: an F row
# in the boundary file would go dead in every boundary run and fail that
# gate, exactly as W rows needed isaxcheck_fixups.txt.
#
# Author: Maccoy Merrell
# SPDX-License-Identifier: GPL-2.0-or-later
#
# WHY THESE ISAs.  This layer is the static-decode oracle the owner named
# for mipsel and aarch64, the two ISAs with no external ground truth (no
# PIN, no Spike): it is what must alert when the QEMU-execution-derived
# register capture of the behavioural-oracle arc disagrees with what the
# trace records today.  x86_64 and riscv64 close that loop through PIN and
# Spike as well, so the layer is a SECOND opinion there rather than the
# only one -- but a second opinion that is gated is worth more than one
# that is not, and the residual that kept riscv64 out is now triaged
# (#169, below).
#
# x86_64 IS STILL ABSENT, and for a stated reason rather than an omission:
# its sweep had not completed when this section was written.  An earlier
# attempt was killed by a 900 s timeout and reported "0 NEW rows", which
# is a TIMEOUT'S output and not a clean sweep -- do not quote it as one.
# Until a completed x86_64 sweep exists and its residual is triaged the
# same way, x86_64 is NOT vouched for by this file and the gate does not
# run it.
#
# THE ROWS ARE THE OBSERVED RESIDUAL, EXACTLY.  Every row was produced by
# a full sweep (151.0 M mipsel / 163.6 M aarch64 encodings, Capstone
# 6.0.0-Alpha7, LLVM per the gate's summary line) and triaged into the
# family comments below; the D (decode-agreement / subtarget-gap) class is
# absent because the fields gate runs --classes=MBR — decode agreement is
# the boundary gate's property, gated there.  No wildcards: an exact row
# goes DEAD the moment either decoder or the dependency model moves, and
# the gate fails on dead rows, which is the tripwire that keeps this file
# maintained.  Do not edit a line to make the gate green.
#
# MOST OF THIS RESIDUAL IS THE BOUNDARY RESIDUAL SEEN ONE LAYER DOWN.
# The fields are the boundary plus the plugin's repairs, so where the
# plugin repairs nothing, a boundary disagreement passes straight
# through; those families cross-reference the boundary family in
# isaxcheck_allow.txt, whose comments carry the verification.  What is
# genuinely NEW at this layer is the plugin's own classification: the
# trap / MOPS / return branch taxonomy, prefetch-as-load memop modeling,
# and the system-register writes the tracer records that LLVM's
# instruction descriptions structurally cannot name.

# Control-flow the ISA table classifies and LLVM's per-opcode flags do
# not.  Traps and exception returns (break / syscall / sdbbp / eret /
# deret) are BRANCH_SYSCALL_TYPE-class on the fields side because the BB
# chain must seal a true BB at a trap — the same deliberate
# classification the fixups file asserts for the aarch64 trap space, and
# the same reason.  jalr.hb is a genuine jump-and-link (hazard-barrier
# form) whose LLVM description carries no branch flag at all.  The two
# `jr` rows are the operand-dependent cases per-opcode flags cannot
# express: `jr $ra` IS a return (fields say so, LLVM's JR cannot), and
# the jalr-with-rd=$zero alias links nothing (LLVM's JALR says call,
# fields correctly say plain indirect branch).  Boundary twin:
# `mipsel B-ret-mismatch jr cs-ret`.  Verified by --hex probes of
# 0c000000 (syscall) and 0800e003 (jr $ra), 2026-08-12.
mipsel FB-call-mismatch jr cs-nocall
mipsel FB-flow-presence break cs-yes llvm-no
mipsel FB-flow-presence deret cs-yes llvm-no
mipsel FB-flow-presence eret cs-yes llvm-no
mipsel FB-flow-presence jalr.hb cs-yes llvm-no
mipsel FB-flow-presence sdbbp cs-yes llvm-no
mipsel FB-flow-presence syscall cs-yes llvm-no
mipsel FB-ret-mismatch jr cs-ret

# llvm mayLoad=0 mayStore=0 on a load.

mipsel FM-cs-mem-llvm-none suxc1

# LWL / LWR read their own destination: the register keeps its unwritten
# bytes, so the old value is a true source.  The boundary's partial-merge
# workaround supplies the read (see the lwl/lwr entries in
# isaxcheck_allow.txt and the ambiguity-probe arc that added it); LLVM
# models the merge as a tied operand only on its store side, so its read
# set stays empty here.  The fields side is the CORRECT one.  Verified
# --hex=00000188: fields SRC{REG_GPR1,...} on lwl $at.
mipsel FR-rd-phantom lwl +REG_FP_REG
mipsel FR-rd-phantom lwl +REG_GPR#
mipsel FR-rd-phantom lwl +REG_LR
mipsel FR-rd-phantom lwl +REG_SP
mipsel FR-rd-phantom lwr +REG_FP_REG
mipsel FR-rd-phantom lwr +REG_GPR#
mipsel FR-rd-phantom lwr +REG_LR
mipsel FR-rd-phantom lwr +REG_SP

# DSPControl, which the tracer folds onto REG_FLAGS: bposge32 branches
# on its pos field (read), rddsp copies fields out of it (read), wrdsp
# writes fields into it (write), and mthlip both reads and increments
# pos (the read is the row; the write both sides agree on).  LLVM models
# no DSPControl use for any of them beyond mthlip's def.  The fields
# side is correct throughout.  Boundary twins: the `+dsp` rows.
mipsel FR-rd-phantom bposge32 +REG_FLAGS
mipsel FR-rd-phantom mthlip +REG_FLAGS
mipsel FR-rd-phantom rddsp +REG_FLAGS
mipsel FR-wr-phantom wrdsp +REG_FLAGS

# LLVM gives the FP condition branches (bc1t / bc1f and the -likely
# forms) an implicit def of $at, modelling its own long-branch assembler
# macro expansion rather than the architecture; the instruction writes
# no GPR.  Keeping the def would fabricate a WAW hazard on $at across
# every FP branch.  Boundary twin family: `mipsel R-wr-missing bc1* +r#`
# (whose comment carries the full story).  Verified --hex=00000145:
# llvm WR{r1} on bc1t.
mipsel FR-wr-missing bc1f +REG_GPR#
mipsel FR-wr-missing bc1fl +REG_GPR#
mipsel FR-wr-missing bc1t +REG_GPR#
mipsel FR-wr-missing bc1tl +REG_GPR#

# CTCMSA — copy TO an MSA control register — is one disagreement seen
# from two sides: LLVM's MCInstrDesc carries the control register as a
# USE (so it sits in LLVM's read set, mapped through the register table
# to REG_SYS), while Capstone and the tracer make it the DEF a
# copy-to-control-register instruction plainly writes (the tracer's MSA
# control id folds onto REG_FCSR).  Capstone and the tracer are correct.
# Boundary twins: `mipsel R-rd-missing ctcmsa +cop#` /
# `R-wr-phantom ctcmsa +cop#`, same single difference in the boundary
# vocabulary.
mipsel FR-rd-missing ctcmsa +REG_SYS
mipsel FR-wr-phantom ctcmsa +REG_FCSR

# The exception-generation space — svc / hvc / smc / brk / hlt / udf /
# dcps<n> — classified BRANCH_SYSCALL_TYPE by the ISA table so the BB
# chain seals a true BB at the trap; none of them carries a control-flow
# flag in LLVM.  SVC is the load-bearing member: every system call in an
# AArch64 trace is one.  DRPS is the deliberate reversal — LLVM calls
# the debug-state exception return a branch and the table does not,
# because it is not an edge any consumer can follow.  This is the same
# classification isaxcheck_fixups.txt asserts (its aarch64 trap section
# carries the full story); boundary twins:
# `aarch64 B-flow-presence hvc / smc / svc`.

# THE AArch64 LOAD-EXCLUSIVES, and the reason they only became visible at
# 733a65dfb0.  LLVM sets mayStore on ldxr / ldaxr / ldxp / ldaxp (with the
# byte and halfword forms) the same way it sets it on the barriers above:
# the exclusive monitor is unmodelled state, and mayStore is how the
# scheduler is told not to move memory across it.  Architecturally a
# load-exclusive reads memory and marks the monitor; it writes nothing.
#
# Until 733a65dfb0 nothing appeared here, and that was two errors
# cancelling rather than agreement: Capstone 6.0.0-Alpha7 reports
# READ|WRITE on the MEM operand of these forms, so the boundary claimed a

# corrected (cap_aarch64_exclusive_mem_access), and the disagreement it
# leaves is LLVM's alone.

# ldaxr entry declared `st[%gp1]` with no address and every execution
# delivered only `ld=`, never `st=` -- a slot QEMU's memop callbacks can
# never fill.  ldar is the control (READ only, unchanged) and the LSE
# read-modify-writes (ldadd, swp) keep both slots, so this is specific to
# the exclusives rather than a blanket rule about acquire/release.
# Evidence: /mnt/md0/QEMU/cst_runs/p3/t177/FINDING.md.  Boundary twins:
