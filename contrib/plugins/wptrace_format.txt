wptrace Binary Trace Format — v0.10
=====================================

1. Notation & Primitives
------------------------

All data is packed at the bit level, LSB-first within each byte.
There are no alignment requirements — fields begin at arbitrary bit
positions.

                Byte layout (LSB-first packing)
                ┌───────────────────────────────┐
         bit 0  │ b0  b1  b2  b3  b4  b5  b6  b7 │  ← first byte
                └───────────────────────────────┘
         bit 8  │ b8  b9 b10 b11 b12 b13 b14 b15 │  ← second byte
                └───────────────────────────────┘

  bits(N)     Fixed-width field of N bits, packed LSB-first.
  ULEB128     Unsigned LEB128: 7 data bits per byte, MSB = continue.
              Zero encodes as a single 0x00 byte.
  SLEB128     Signed LEB128: two's complement with sign extension
              from bit 6 of the final byte.
  string      ULEB128 length N, then N raw UTF-8 bytes (each 8 bits).
              Empty string = ULEB128(0), no bytes follow.


2. Top-Level Structure
----------------------

A wptrace binary file is a single contiguous bit stream with three
regions.  There are no byte-alignment gaps between regions.

  ┌──────────────────────────────────────────────────────────┐
  │                        HEADER                            │
  │  magic(32) isa(3) flags(8) strings... thread_id(ULEB)   │
  ├──────────────────────────────────────────────────────────┤
  │                         BODY                             │
  │  Sequence of tagged records:                             │
  │    tag=1 (ENTRY)    — correct-path BB + wrong-path chain │
  │    tag=2 (MEMALLOC) — memory map/unmap/remap event       │
  │    tag=3 (SYNC)     — thread switch event                │
  │    tag=0 (END)      — terminates the body                │
  ├──────────────────────────────────────────────────────────┤
  │                        FOOTER                            │
  │  [Thread Segment Directory]   (if FLAG_THREAD_DIR)       │
  │  num_entries(ULEB)            entry count for validation  │
  │  Template table               BB template definitions     │
  └──────────────────────────────────────────────────────────┘


3. Header
---------

Written once at the start of the stream.

  ┌─────────────┬─────────┬────────────────────────────────┐
  │ Field       │ Encoding│ Description                    │
  ├─────────────┼─────────┼────────────────────────────────┤
  │ magic       │ bits(32)│ 0x5450570A ('T','P','W',0x0A)  │
  │ isa         │ bits(3) │ TraceISA enum (see §10)        │
  │ flags       │ bits(8) │ Feature flags (see §3.1)       │
  │ command     │ string  │ QEMU command line              │
  │ datetime    │ string  │ Trace start timestamp          │
  │ comment     │ string  │ User-supplied comment          │
  │ target_name │ string  │ ISA name ("x86_64", etc.)      │
  │ thread_id   │ ULEB128 │ Thread ID (0 = single-thread)  │
  └─────────────┴─────────┴────────────────────────────────┘

Example bit layout for an x86_64 single-thread trace with no optional
features:

  bit 0                          31 32  34 35      42
  ┌──────────────────────────────┬───┬──────────┐
  │  0x5450570A  (32 bits)       │001│ 00000000 │  ...strings...
  └──────────────────────────────┴───┴──────────┘
   magic                         isa  flags=0x00


3.1  Header Flags
~~~~~~~~~~~~~~~~~

  ┌─────┬────────────────────┬───────────────────────────────────┐
  │ Bit │ Name               │ Effect                            │
  ├─────┼────────────────────┼───────────────────────────────────┤
  │  0  │ WPT_FLAG_MEM_DATA  │ Load/store data values present    │
  │  1  │ WPT_FLAG_REG_DATA  │ Register values (reserved)        │
  │  2  │ WPT_FLAG_MEM_ALLOC │ Memory allocation events present  │
  │  3  │ WPT_FLAG_THREADS   │ Multi-thread mode active          │
  │  4  │ WPT_FLAG_THREAD_DIR│ Thread Segment Directory in footer│
  │ 5-7 │ (reserved)         │                                   │
  └─────┴────────────────────┴───────────────────────────────────┘

When THREADS is set, the body contains SYNC_THREAD_SWITCH events and
the footer contains a segment directory (THREAD_DIR is also set).
When MEM_DATA is set, every dyn-param record in the body is followed
by its data value encoding.


4. Body Records
---------------

The body is a sequence of tagged records.  Each begins with a 2-bit
tag:

  tag bits(2)
  ┌────┐
  │ 00 │  END      — sentinel, terminates body
  │ 01 │  ENTRY    — correct-path BB execution + wrong-path chain
  │ 10 │  MEMALLOC — memory allocation event
  │ 11 │  SYNC     — synchronisation / thread-switch event
  └────┘


4.1  BODY_TAG_ENTRY (tag=1) — BB Execution Record
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

This is the primary record type.  Each represents one correct-path
basic block execution, optionally followed by a chain of wrong-path
BBs (the Smith-predicted wrong-path continuation).

  ┌─────────────────────────────────────────────────────────────┐
  │ tag                  bits(2) = 1                            │
  │ template_delta       SLEB128   (current - prev template_id) │
  │ cp_unchanged         bits(1)   (1=dyn params identical)     │
  │ [cp_dyn_patch]       §5        (only if cp_unchanged=0)     │
  │ [cp_mem_data]        §6        (only if FLAG_MEM_DATA)      │
  │ num_wp               ULEB128   (wrong-path BB count)        │
  │ ── for each wrong-path BB ──                                │
  │ │ wp_template_delta  SLEB128   (current - prev wp tmpl id)  │
  │ │ wp_unchanged       bits(1)                                │
  │ │ [wp_dyn_patch]     §5        (only if wp_unchanged=0)     │
  │ │ [wp_mem_data]      §6        (only if FLAG_MEM_DATA)      │
  │ num_wp_events        ULEB128   (faults + xlat errors)       │
  │ ── for each wp event ──                                     │
  │ │ wp_index_gap       ULEB128   (idx - (prev_idx + 1))       │
  │ │ xlat_unavailable   bits(1)                                │
  │ │ fault              bits(1)                                │
  │ │ [fault_detail]     §4.1.1    (only if fault=1)            │
  └─────────────────────────────────────────────────────────────┘

Template IDs are delta-encoded: the first entry stores its ID relative
to 0; subsequent entries store the difference from the previous entry's
template ID.  Wrong-path template deltas are relative to the previous
WP template within the same entry (starting from 0).

The cp_unchanged / wp_unchanged bit is an optimization: when a BB is
re-executed with the exact same set of memory addresses and types as
the last time that template was seen, the dyn_patch is omitted entirely
and the reader reuses the prior state.  Note: when MEM_DATA is set,
the data values are still written even if unchanged=1 because the
addresses haven't changed but the data might have.


4.1.1  Fault Detail
~~~~~~~~~~~~~~~~~~~

Appended to a wrong-path event when fault=1:

  ┌───────────────────────────────────────────────────┐
  │ stop_reason        bits(8)   WPStopReason enum    │
  │ has_exception      bits(1)                        │
  │ [exception_id]     bits(8)   GenericExceptionId   │
  │ [has_exc_reg]      bits(1)                        │
  │ [exc_reg_id]       bits(8)   GenericRegId         │
  │ poison_len         ULEB128   effective mask length │
  │ [poison_bytes]     poison_len × bits(8)           │
  └───────────────────────────────────────────────────┘

The poison mask is a per-instruction bitmask over the wrong-path BB:
byte[i] != 0 means instruction i was poisoned (consumed a value
produced by a faulting earlier WP instruction).  The mask is trimmed
to its last non-zero byte.


4.2  BODY_TAG_MEMALLOC (tag=2) — Memory Allocation Event
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Tracks mmap/munmap/mremap events from the traced program.

  ┌─────────────────────────────────────────────┐
  │ tag           bits(2) = 2                   │
  │ event_type    bits(2)                       │
  │               0 = MAP                       │
  │               1 = UNMAP                     │
  │               2 = REMAP                     │
  │ vaddr         ULEB128                       │
  │ size          ULEB128                       │
  │ [new_vaddr]   ULEB128   (REMAP only)        │
  │ [new_size]    ULEB128   (REMAP only)        │
  └─────────────────────────────────────────────┘


4.3  BODY_TAG_SYNC (tag=3) — Synchronisation Event
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Emitted when QEMU switches execution from one vCPU to another.

  ┌──────────────────────────────────────────────┐
  │ tag           bits(2) = 3                    │
  │ sync_type     bits(4)                        │
  │               4 = THREAD_SWITCH              │
  │ [thread_id]   ULEB128   (THREAD_SWITCH only) │
  └──────────────────────────────────────────────┘

SYNC_THREAD_SWITCH carries the mapped thread_id (monotonic, 0-based)
of the thread that is now executing.  The thread_id corresponds to
entries in the Thread Segment Directory (§8).

SYNC_ATOMIC (type=5) is not emitted as a body-level event — it only
appears as a sync_hint annotation on individual instructions within
templates (§7).


4.4  BODY_TAG_END (tag=0) — Body Terminator
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

  ┌─────────────────┐
  │ tag  bits(2) = 0│
  └─────────────────┘

Immediately followed by the footer (§8, §9).


5. Dynamic Parameter Patch Encoding
------------------------------------

Each BB execution produces a set of dynamic parameters — one per
memory-accessing instruction (loads and stores), recording the virtual
address accessed at runtime.

Parameters are tracked per-template: on first execution of template T,
the full parameter set is written; on subsequent executions, only the
changed positions are delta-encoded against the previous execution of
the same template.

  ┌──────────────────────────────────────────────────────────┐
  │ new_len        ULEB128   total param count this execution│
  │ num_changed    ULEB128   how many positions differ       │
  │ ── for each changed position (prev_pos starts at -1) ── │
  │ │ pos_gap      ULEB128   pos - (prev_pos + 1)           │
  │ │ type_bit     bits(1)   0=load  1=store                │
  │ │ delta        SLEB128   cur_value - base_value          │
  │ └───────────────────────────────────────────────────────│
  └──────────────────────────────────────────────────────────┘

base_value is the value at the same position from the previous
execution of this template (or 0 if the position is new).  The delta
is a signed 64-bit difference, so addresses that move by small amounts
between executions compress to small SLEB128 values.

Example — a load at 0x7fff1000, then re-executed at 0x7fff1008:

  First execution:   new_len=1 num_changed=1 pos_gap=0 type=0 delta=0x7fff1000
  Second execution:  unchanged=1  (if address identical)
   or:               new_len=1 num_changed=1 pos_gap=0 type=0 delta=+8


6. Memory Data Encoding (FLAG_MEM_DATA)
---------------------------------------

When MEM_DATA is enabled, every dyn-param (for both correct-path and
wrong-path) is followed by its data value — the actual bytes
loaded/stored at that address.

Data values are encoded per-param, in-order, immediately after the
dyn_patch (or after the unchanged bit if unchanged=1):

  ┌──────────────────────────────────────────────────────┐
  │ ── for each dyn param ──                             │
  │ │ size_code    bits(3)   index into size table below  │
  │ │ data_bytes   size × bits(8)   little-endian         │
  │ └────────────────────────────────────────────────────│
  └──────────────────────────────────────────────────────┘

  Size table (3-bit code → byte count):
  ┌──────┬───┬───┬───┬───┬────┬───┬───┬───┐
  │ code │ 0 │ 1 │ 2 │ 3 │  4 │ 5 │ 6 │ 7 │
  │ bytes│ 1 │ 2 │ 4 │ 8 │ 16 │ 1 │ 1 │ 1 │
  └──────┴───┴───┴───┴───┴────┴───┴───┴───┘

For sizes > 8 bytes (code=4, 16 bytes), the low 8 bytes are written
first, followed by the high 8 bytes — both little-endian.


7. Template Table (Footer)
--------------------------

Templates define the static properties of each basic block.  The body
references templates by ID; the template table provides the instruction
details needed to reconstruct the full trace.

Written after the entry count in the footer:

  ┌──────────────────────────────────────────────────────┐
  │ num_templates    ULEB128                             │
  │ ── for each template ──                              │
  │ │ template_id    ULEB128                             │
  │ │ start_pc       ULEB128                             │
  │ │ n_insns        ULEB128                             │
  │ │ fall_through_pc ULEB128                            │
  │ │ sym_name_len   ULEB128                             │
  │ │ sym_name_bytes sym_name_len × bits(8)              │
  │ │ ── for each instruction ──                         │
  │ │ │ pc               ULEB128                         │
  │ │ │ opcode           bits(8)   GenericOpcode          │
  │ │ │ branch_type      bits(8)   BranchType             │
  │ │ │ branch_cond      bits(1)                          │
  │ │ │ n_src_regs       bits(3)   (max 7)                │
  │ │ │ n_dst_regs       bits(3)   (max 7)                │
  │ │ │ has_immediate    bits(1)                          │
  │ │ │ sync_hint        bits(4)   SyncEventType          │
  │ │ │ src_regs         n_src × bits(8) GenericRegId     │
  │ │ │ dst_regs         n_dst × bits(8) GenericRegId     │
  │ │ │ [immediate]      SLEB128  (if has_immediate=1)    │
  │ │ │ insn_size        ULEB128  (byte count)            │
  │ │ │ raw_bytes        insn_size × bits(8)              │
  │ │ └─────────────────────────────────────────────────│
  │ └──────────────────────────────────────────────────│
  └──────────────────────────────────────────────────────┘

Per-instruction bit-level layout:

  ┌───────────┬───────────┬─────┬─────┬─────┬─────┬──────┐
  │ opcode(8) │ branch(8) │bc(1)│ns(3)│nd(3)│hi(1)│sh(4) │
  └───────────┴───────────┴─────┴─────┴─────┴─────┴──────┘
                                                    28 bits fixed
  followed by: src_regs[ns×8], dst_regs[nd×8], [imm], size, raw_bytes

The sync_hint field marks instructions that perform atomic/locked
memory operations (sync_hint=5=SYNC_ATOMIC).  The trace consumer
uses these annotations in combination with the memory addresses from
the corresponding dyn-param to identify synchronisation objects.


8. Thread Segment Directory (Footer)
-------------------------------------

Present when FLAG_THREAD_DIR is set.  Written between BODY_TAG_END
and the entry count.

  ┌──────────────────────────────────────────────────────────┐
  │ num_segments       ULEB128                               │
  │ ── for each segment (in body order) ──                   │
  │ │ thread_id        ULEB128   monotonic (0 = main thread) │
  │ │ body_bit_offset  ULEB128   bit position of first entry │
  │ │ num_entries      ULEB128   BB entry count              │
  │ │ flags            bits(8)   bit 0 = is_atomic           │
  │ │ num_atomic_addrs ULEB128                               │
  │ │ atomic_addrs     num_atomic_addrs × ULEB128            │
  │ └──────────────────────────────────────────────────────│
  └──────────────────────────────────────────────────────────┘

A thread segment is a contiguous run of BODY_TAG_ENTRY records from a
single thread.  Segment boundaries occur at:

  1. SYNC_THREAD_SWITCH — execution moved to a different vCPU.
  2. Atomic BB isolation — a BB whose template contains any
     SYNC_ATOMIC instruction is emitted as its own 1-entry segment,
     with breaks before and after.

Atomic segments (flags bit 0 = 1) contain exactly one BB and list
the virtual addresses of all atomic memory operations performed.
Two atomic segments from different threads that share any address
are in conflict and must execute in body order.


9. Complete Footer Layout
-------------------------

After BODY_TAG_END:

  ┌─────────────────────────────────────────────┐
  │  [Thread Segment Directory]   §8            │
  │  num_entries    ULEB128  (validation count)  │
  │  Template Table              §7              │
  └─────────────────────────────────────────────┘

Readers that do not understand FLAG_THREAD_DIR will not know to skip
the directory; this is intentional — the magic version (0x0A)
rejects old readers.


10. Enumerations
----------------

10.1  TraceISA — bits(3)

  ┌───┬───────────┐
  │ 0 │ unknown   │
  │ 1 │ x86_64    │
  │ 2 │ aarch64   │
  │ 3 │ riscv64   │
  │ 4 │ mipsel    │
  └───┴───────────┘

10.2  GenericOpcode — bits(8)

  ┌────┬──────────┬────┬──────────┬────┬──────────┐
  │  0 │ UNKNOWN  │ 18 │ POP      │ 36 │ VEC_ADD  │
  │  1 │ INT_ADD  │ 19 │ LEA      │ 37 │ VEC_SUB  │
  │  2 │ INT_SUB  │ 20 │ MOVSX    │ 38 │ VEC_MUL  │
  │  3 │ INT_MUL  │ 21 │ MOVZX    │ 39 │ VEC_MOV  │
  │  4 │ INT_DIV  │ 22 │ XCHG     │ 40 │ VEC_SHUF │
  │  5 │ AND      │ 23 │ CMP      │ 41 │ VEC_LOGIC│
  │  6 │ OR       │ 24 │ TEST     │ 42 │ NOP      │
  │  7 │ XOR      │ 25 │ BRANCH   │ 43 │ SYSCALL  │
  │  8 │ NOT      │ 26 │ CALL     │ 44 │ FENCE    │
  │  9 │ SHL      │ 27 │ RET      │ 45 │ CMOV     │
  │ 10 │ SHR      │ 28 │ FP_ADD   │ 46 │ SETCC    │
  │ 11 │ SAR      │ 29 │ FP_SUB   │ 47 │ INT_ADC  │
  │ 12 │ ROL      │ 30 │ FP_MUL   │ 48 │ INT_SBB  │
  │ 13 │ ROR      │ 31 │ FP_DIV   │ 49 │ NEG      │
  │ 14 │ MOV      │ 32 │ FP_SQRT  │ 50 │ INC      │
  │ 15 │ LOAD     │ 33 │ FP_MOV   │ 51 │ DEC      │
  │ 16 │ STORE    │ 34 │ FP_CVT   │ 52 │ INT_MADD │
  │ 17 │ PUSH     │ 35 │ FP_CMP   │ 53 │ INT_MSUB │
  └────┴──────────┴────┴──────────┴────┴──────────┘
  ┌────┬──────────┐
  │ 54 │ FP_MADD  │  Fused FP multiply-add  (FMADD, VFMADD*, FMLA)
  │ 55 │ FP_MSUB  │  Fused FP multiply-sub  (FMSUB, VFMSUB*, FMLS)
  │ 56 │ INT_REM  │  Integer remainder       (REM, REMU)
  │ 57 │ INT_MULH │  Integer multiply-high   (MULH, SMULH, UMULH)
  │ 58 │ VEC_MADD │  Vector multiply-accum.  (MLA, SMLAL, MADDV)
  │ 59 │ BITMANIP │  Bit manipulation        (CLZ, CTZ, POPCNT, BSWAP)
  │ 60 │ CRYPTO   │  Cryptographic ops       (AES, SHA, CRC32)
  └────┴──────────┘

  Opcodes 52-60 distinguish operations with significantly different
  latencies from their base category.  For example, fused multiply-add
  (FP_MADD) has different pipeline timing than a plain FP_MUL on most
  microarchitectures.  INT_REM separates remainder from division, and
  INT_MULH separates multiply-high (which may have different latency
  than a plain multiply on some designs).  BITMANIP and CRYPTO cover
  instructions that often use dedicated functional units.

10.3  BranchType — bits(8)

  ┌───┬───────────────┐
  │ 0 │ NONE          │
  │ 1 │ DIRECT_JUMP   │
  │ 2 │ INDIRECT_JUMP │
  │ 3 │ DIRECT_CALL   │
  │ 4 │ INDIRECT_CALL │
  │ 5 │ RETURN        │
  │ 6 │ SYSCALL       │
  │ 7 │ COND_DIRECT   │
  └───┴───────────────┘

10.4  SyncEventType — bits(4)

  ┌───┬────────────────┐
  │ 0 │ NONE           │
  │ 4 │ THREAD_SWITCH  │
  │ 5 │ ATOMIC         │
  └───┴────────────────┘

  THREAD_SWITCH appears as a BODY_TAG_SYNC record.
  ATOMIC appears only as sync_hint on template instructions.

10.5  GenericExceptionId — bits(8)

  ┌───┬────────────────────┐
  │ 0 │ NONE               │
  │ 1 │ UNKNOWN            │
  │ 2 │ INT_DIVIDE_BY_ZERO │
  │ 3 │ FP_DIVIDE_BY_ZERO  │
  │ 4 │ MEMORY_ACCESS      │
  └───┴────────────────────┘

10.6  WPStopReason — bits(8)

  ┌───┬──────────────────┐
  │ 0 │ NONE             │
  │ 1 │ SYSCALL_USERMODE │
  └───┴──────────────────┘

10.7  GenericRegId — bits(8)

  ┌─────────┬──────────────────────────────────────┐
  │    0    │ NONE                                  │
  │  1- 64 │ GPR0-GPR63  (general-purpose)          │
  │ 65-128 │ FPR0-FPR63  (floating-point)           │
  │129-192 │ VEC0-VEC63  (vector/SIMD)              │
  │   249  │ ZERO        (hardwired zero register)  │
  │   250  │ SP          (stack pointer)             │
  │   251  │ FLAGS       (condition flags)           │
  │   252  │ IP          (instruction pointer)       │
  │   253  │ LR          (link register)             │
  │   254  │ FP          (frame pointer)             │
  └─────────┴──────────────────────────────────────┘

  The ZERO register (249) represents ISA registers that are hardwired
  to always produce zero on read.  ISA-specific mappings:
    riscv64: X0 (zero) → ZERO
    mipsel:  $0 ($zero) → ZERO
    aarch64: XZR / WZR  → ZERO
    x86_64:  (no zero register)

  ISA-specific mappings (GPR0-31):
    x86_64:  GPR0=RAX GPR1=RCX GPR2=RDX GPR3=RBX GPR4=RSI GPR5=RDI
             GPR6-GPR13=R8-R15
    aarch64: GPR0-GPR30=X0-X30
    riscv64: GPR0-GPR31=X0-X31  (X0 maps to ZERO, not GPR0)
    mipsel:  GPR0-GPR31=$0-$31  ($0 maps to ZERO, not GPR0)

  FPR and VEC ranges follow per-ISA conventions.

10.8  MemAllocEventType — bits(2)

  ┌───┬────────┐
  │ 0 │ MAP    │
  │ 1 │ UNMAP  │
  │ 2 │ REMAP  │
  └───┴────────┘


11. Worked Example: Reading a Body Entry
-----------------------------------------

Given a correct-path BB execution of template 5 (previous template
was 3), with one load at address 0x4000, followed by a single
wrong-path BB (template 8) that faulted:

  Stream (conceptual, not actual bit values):

  01                          ← tag = ENTRY
  SLEB(+2)                   ← template_delta = 5-3
  0                           ← cp_unchanged = 0, dyn params changed
    ULEB(1) ULEB(1)           ← new_len=1, num_changed=1
    ULEB(0)                   ← pos_gap=0 (position 0)
    0                         ← type_bit=0 (load)
    SLEB(0x4000)              ← delta (first time, base=0)
  ULEB(1)                     ← num_wp = 1
    SLEB(+8)                  ← wp_template_delta = 8-0
    0                         ← wp_unchanged = 0
      ULEB(0) ULEB(0)         ← new_len=0, num_changed=0 (no mem ops)
  ULEB(1)                     ← num_wp_events = 1
    ULEB(0)                   ← wp_index_gap = 0 (event for wp[0])
    0                         ← xlat_unavailable = 0
    1                         ← fault = 1
      00000001                ← stop_reason = SYSCALL_USERMODE
      0                       ← has_exception = 0
      ULEB(0)                 ← poison_len = 0


12. Worked Example: Multi-Thread Trace Layout
----------------------------------------------

Two threads (T0, T1) executing BBs with an atomic spinlock:

  HEADER: magic isa=1 flags=0x18 (THREADS|THREAD_DIR) ...

  BODY:
  ┌────────────────────────────────────────────────────────┐
  │ ENTRY  BB100 [load=0x1000]        ← T0, segment S0   │  ← bit offset A
  │ ENTRY  BB101 [load=0x1008]        ← T0, segment S0   │
  │ ENTRY  BB101 [load=0x1008]        ← T0, segment S0   │
  ├ ── T0 segment S0 closed (3 entries) ──────────────────┤
  │ ENTRY  BB102 [store=0x2000]       ← T0, segment S1   │  ← bit offset B
  │        (template has sync_hint=ATOMIC on lock xchg)   │
  ├ ── T0 atomic segment S1 closed (1 entry) ─────────────┤
  │ ENTRY  BB103 [load=0x1010]        ← T0, segment S2   │  ← bit offset C
  │ ENTRY  BB104 []                   ← T0, segment S2   │
  ├ ── T0 segment S2 closed (thread switch) ──────────────┤
  │ SYNC   type=THREAD_SWITCH thread=1                    │
  │ ENTRY  BB200 [load=0x3000]        ← T1, segment S3   │  ← bit offset D
  │ ENTRY  BB201 [load=0x3008]        ← T1, segment S3   │
  ├ ── T1 segment S3 closed ──────────────────────────────┤
  │ ENTRY  BB202 [store=0x2000]       ← T1, segment S4   │  ← bit offset E
  │        (template has sync_hint=ATOMIC on lock xchg)   │
  ├ ── T1 atomic segment S4 closed (1 entry) ─────────────┤
  │ ENTRY  BB203 []                   ← T1, segment S5   │  ← bit offset F
  ├ ── T1 segment S5 closed (thread switch) ──────────────┤
  │ SYNC   type=THREAD_SWITCH thread=0                    │
  │ ENTRY  BB105 [load=0x1018]        ← T0, segment S6   │  ← bit offset G
  │ END                                                   │
  └────────────────────────────────────────────────────────┘

  FOOTER:
  ┌─────────────────────────────────────────────────────────┐
  │ Thread Segment Directory:                               │
  │  num_segments = 7                                       │
  │                                                         │
  │  S0: tid=0 offset=A entries=3 flags=0x00 addrs=0        │

  │  S5: tid=1 offset=F entries=1 flags=0x00 addrs=0        │
  │  S6: tid=0 offset=G entries=1 flags=0x00 addrs=0        │
  ├─────────────────────────────────────────────────────────┤
  │ num_entries = 11                                        │
  │ Template Table: BB100, BB101, BB102, BB103, BB104,      │
  │                 BB105, BB200, BB201, BB202, BB203        │
  └─────────────────────────────────────────────────────────┘

  S1 and S4 both touch address 0x2000 → conflict edge.
  ChampSim must execute S1 before S4 (body order).

  Scheduling:
    T0: S0 → S1 → S2 → S6
    T1:           S3 → S4 → S5
    Constraint: S1 before S4 (shared atomic addr 0x2000)
    Spawn: T1 becomes schedulable after S2 completes
           (first T1 segment S3 appears after S2 in body)

14. Design Rationale
--------------------

Bit-level packing:  Traces can contain billions of entries.  Byte-
aligned fields would waste 30-50% of space on padding.  The LSB-first
packing produces a simple state machine that needs only a single-byte
buffer and a 3-bit position counter.

Delta + SLEB128 for template IDs:  Most BB transitions are to nearby
templates (the same hot loop).  Delta encoding reduces most template
references to 1-2 byte SLEB128 values.

Dyn-param patch encoding:  BBs in hot loops re-execute with addresses
that differ by the stride of the loop.  Position-gap + delta encoding
reduces each re-execution to a few bytes for the changed positions.

Templates in footer:  Templates are discovered incrementally during
execution.  Writing them to the footer avoids reserving space or
backpatching.  The reader must buffer body entries and resolve template
references in a second pass (or stream the body and look up templates
by ID as they arrive from the footer).

Segment directory for threading:  Body-level interleaving preserves
QEMU execution order.  The directory enables random access to specific
thread segments and provides the metadata (body offsets, atomic
addresses) needed for conflict-aware scheduling without scanning the
body.
