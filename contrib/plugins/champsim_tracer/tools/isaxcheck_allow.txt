# isaxcheck allowlist — justified residual decoder-metadata disagreements.
#
# Author: Maccoy Merrell
# SPDX-License-Identifier: GPL-2.0-or-later
#
# isaxcheck compares the decode metadata the ChampSim Tracer actually
# consumes (cap_disas_raw_detail() from disas/capstone.c — Capstone plus
# every correction the boundary applies) against the LLVM MC layer, over an
# exhaustive sweep of the opcode-bearing encoding space.  Anything it reports
# that is not listed here fails the gate.
#
# Format:  <isa> <signature key>
#          `#` starts a comment; `*` in the key is a glob wildcard.
# Signature keys are `CLASS mnemonic [qualifier]`, where the qualifier for
# the register classes is the difference set with register numbers collapsed
# to `#` (so `+r#` means "some general-purpose register", `+za` means "the
# SME accumulator tile").
#
# EVERY ENTRY BELOW NAMES: what the disagreement is, why it is not a tracer
# defect, and how to check whether it can be deleted.  An entry that cannot
# carry those three things is a bug to fix, not a line to add here.
#
# Observed against Capstone 6.0.0-Alpha7 (subprojects/capstone.wrap) and
# LLVM 18 MC.  On a Capstone bump: rebuild, re-run
# `python -m champsim_tracer_validator full`, and delete every entry whose
# signature no longer appears.  `capstone_workaround_probe` answers the
# complementary question — whether an existing disas/capstone.c workaround
# has become unnecessary.

# =====================================================================
# 1. Where LLVM is the one that is wrong, or models something that is not
#    architectural.  These are not Capstone defects and never will be
#    "fixed"; they are removable only if LLVM's own descriptions change.
# =====================================================================

# LLVM's MIPS BC1T/BC1F/BC1TL/BC1FL carry `Defs = [AT]`, an ASSEMBLER-MACRO
# artifact: the assembler may expand a long-range FP branch through $at, so
# the pseudo-instruction claims to clobber it.  A branch writes no GPR at
# all.  Capstone inherited the same claim through the TableGen sync, and
# disas/capstone.c now removes it (see the FP condition-code workaround) —
# which is exactly why this shows up as "Capstone is missing a write".
# Keeping the phantom would fabricate a WAW hazard on $at across every FP
# branch.  Removable when LLVM stops modelling the macro expansion in
# MCInstrDesc, which is not expected.
mipsel R-wr-missing bc1* +r#

# (The MIPS branch-and-link and JR / JALR target-read entries that used to
# sit here were an artifact of this tool, not a disagreement.  Its call-site
# suppression of LLVM's AArch64 ABI stack-pointer use spelled the non-
# AArch64 register `r2` — the RISC-V stack pointer — and applied it to every
# ISA, so on MIPS it deleted $v0 from the read set of anything LLVM calls a
# call.  `jalr $t0` compared clean and `jalr $v0` did not; signature keys
# collapse register numbers, so one erased value read as a class-wide LLVM
# defect.  The justification that stood here said LLVM "reports no reads at
# all" for these forms.  It never did.)
mipsel B-ret-mismatch jr cs-ret

# (LWL/LWR read their own destination — the partial-merge workaround in
# disas/capstone.c supplies it, LLVM models the merge as a tied operand on
# the *store* side only.  Covered by the explicit `lwl` / `lwr` entries in
# section 3; the class-wide form that used to live here spelled the family
# `lw[lr]`, which the matcher reads literally — `*` is its only wildcard —
# so it never matched anything.)

# LLVM gives every SSE/AVX-class RISC-V FP vector op `Uses = [FRM]` but, in
# LLVM 18, drops the `[VL, VTYPE]` the base class supplies — so the FP
# vector ops claim not to depend on the vector configuration that decides
# how many elements they process.  Architecturally they do, and
# disas/capstone.c supplies the reads (see the RVV vector-configuration
# workaround).  Removable when LLVM's RISCVInstrInfoV* descriptions carry
# VL/VTYPE on the FP forms; re-check by running this sweep against a newer
# llvm-config.
riscv64 R-rd-phantom vf* +vl,vtype
riscv64 R-rd-phantom vl*.v +vl,vtype
riscv64 R-rd-phantom vs*.v +vl,vtype

# The RVV unconditionally-masked carry/merge families (`.vvm` / `.vxm` /
# `.vim` / `.vfm`) take v0 as a mandatory DATA operand: the carry-in of
# vadc/vmadc, the borrow-in of vsbc/vmsbc, the select control of
# vmerge/vfmerge.  RVV v1.0 §11.4, §11.5 and §11.15 all define it as read.
# BOTH decoders print `v0` in the operand string and NEITHER reports the
# read, so this is the one disagreement class this tool could never have
# discovered — it was fixed from the specification (see the v0 restore in
# cap_fill_generic_operands) and carries its own regression check,
# probe_rv_v0_carry_mask, precisely because the sweep cannot cover it.
# Without the read a multiword add chain's carry serialisation vanishes.
# The unmasked siblings (`vmadc.vv`, `vmsbc.vx`) genuinely do not read v0
# and are deliberately not matched.  Removable when LLVM's
# RISCVInstrInfoV descriptions mark the V0 operand a use.
riscv64 R-rd-phantom vadc.v*m +v#
riscv64 R-rd-phantom vmadc.v*m +v#
riscv64 R-rd-phantom vsbc.v*m +v#
riscv64 R-rd-phantom vmsbc.v*m +v#
riscv64 R-rd-phantom vmerge.v*m +v#
riscv64 R-rd-phantom vfmerge.v*m +v#

# (`aarch64 R-rd-missing bl* +sp` used to sit here, over LLVM's ABI-
# modelling implicit SP use on AArch64 calls.  The suppression it said was
# already working ran BEFORE the loop that inserts the implicit uses, so it
# suppressed nothing at all; the glob then hid every form, plain and
# pointer-authenticated alike.  The suppression happens where the use
# enters now, and none of them disagree.)

# LLVM gives AArch64 MRS/MSR an NZCV def that the architecture does not —
# for MOST members.  The def is attached to the whole
# MSR-immediate-to-PSTATE-field form, because one of the fields it can name
# IS NZCV — so every alias of that form inherits it, including the SME
# streaming-mode switches, which write PSTATE.SM and PSTATE.ZA and leave
# the condition flags alone.
#
# ONE alias under the `mrs` key is the other way around, and this comment
# used to paper over it: `mrs xN, RNDR` / `RNDRRS` really does set NZCV
# (Z reports entropy failure), LLVM is RIGHT to def it there, and Capstone
# reports no flags write — a real Capstone gap riding the same collapsed
# signature as the phantoms (verified --hex=02243bd5, 2026-08-12: llvm
# WR{nzcv,r2}, boundary WR{r2}).  Work item filed; the fields-layer twin in
# isaxcheck_fields_allow.txt carries the same carve-out.  Weight today is
# nil (no traced workload reads RNDR), which is why carrying it is
# tolerable, not why it is right.
aarch64 R-wr-missing mrs +nzcv
aarch64 R-wr-missing msr +nzcv
aarch64 R-wr-missing smstart +nzcv
aarch64 R-wr-missing smstop +nzcv

# The TLBI operations that take NO Xt argument (TLBI VMALLE1, VMALLS12E1IS,
# ALLE2, …) are still encoded in the SYS format, which has an Rt field; the
# architecture requires that field to be 0b11111 for them.  LLVM keeps the
# syntactic operand and reports it read whatever it holds, so an encoding
# that puts a real register number in an Rt the operation does not use looks
# like a lost read.  Capstone is right — the operation reads no register —
# and the disagreement exists only on reserved encodings no assembler emits
# (`tlbi vmalls12e1is` written properly names XZR, which folds away).  The
# argument-taking forms (`tlbi vae2is, x0`) agree on both sides.  Newly
# reachable since the sweep started filling Rn=30 (see sweep_aarch64).
aarch64 R-rd-missing tlbi +r#

# CWD / CDQ / CQO sign-extend the accumulator into the D register and leave
# the accumulator alone.  LLVM's implicit-def list names it anyway --
# llvm_opcode_table.tsv has `OPC CDQ ... IDEF:EAX,EDX, IUSE:EAX,` and the
# same for CQO -- which is the register-allocator convenience LLVM's x86
# implicit lists are known for, not an architectural claim.
#
# The architecture is explicit.  Intel SDM Vol. 2, CWD/CDQ/CQO "Operation":
#   IF OperandSize = 16 THEN DX := SignExtend(AX);
#   ELSE IF OperandSize = 32 EDX := SignExtend(EAX);
#   ELSE IF 64-Bit Mode and OperandSize = 64 RDX := SignExtend(RAX);
# with no assignment to the source and "Flags Affected: None".  XED agrees
# operand for operand -- `xed -64 -v 5 -d 99` gives REG0/W/EDX and
# REG1/R/EAX -- and so does iced-x86.
#
# The boundary drops Capstone's matching phantom (cap_x86_is_sign_extend_to_d)
# because these sit immediately before a signed IDIV: an rax marked written
# makes the trace name the CQO as the dividend's producer and hides the real
# one.  So the tracer is short a write LLVM reports, deliberately.
#
# Delete these three if LLVM ever narrows CDQ/CQO/CWD to Defs = [xDX].
x86_64 R-wr-missing cltd +r#
x86_64 R-wr-missing cqto +r#
x86_64 R-wr-missing cwtd +r#

# =====================================================================
# 2. Deliberate tracer modelling decisions.  The disagreement is real but
#    the tracer's answer is the intended one, so "fixing" it would be a
#    regression.  Removable only if the modelling decision changes.
# =====================================================================

# Memory-hint and cache-maintenance instructions (AArch64 PRF*, MIPS
# PREF/PREFE/CACHE/CACHEE/SYNCI) emit no TCG memop.  The tracer classifies
# them as GEN_OP_PREFETCH / GEN_OP_CACHE_FLUSH and synthesises the address
# slot from the opcode class, so the boundary deliberately leaves their MEM
# operand's access bits empty rather than minting a load lane that no
# memory callback will ever fill — see cap_aarch64_infer_mem_access(), which
# returns 0 for the prefetch classes on purpose, and the GEN_OP_PREFETCH
# comment in champsim_tracer_generic_ids.h.  LLVM reports mayLoad.
aarch64 Z-access0 prf* MEM
aarch64 M-miss-load prf*
mipsel Z-access0 pref* MEM
mipsel Z-access0 cache* MEM
mipsel Z-access0 synci MEM
mipsel M-cs-mem-llvm-none pref*
mipsel M-cs-mem-llvm-none cache*
mipsel M-cs-mem-llvm-none synci

# SVE vector ADR computes an address without accessing memory — the AArch64
# equivalent of x86 LEA.  An access-free MEM operand is the correct
# representation and the operand walker skips it for exactly that reason
# ("LEA / prefetch-hint MEM operands lack both READ and WRITE — no real
# memop, don't count", champsim_tracer_decode.cc).
aarch64 Z-access0 adr MEM
aarch64 M-cs-mem-llvm-none adr

# =====================================================================
# 3. Feature sets the tracer does not model.  These are honest gaps with a
#    named boundary, documented in docs/limitations.rst.
# =====================================================================

# SME.  The ZA matrix accumulator and its tile/slice operands arrive as
# Capstone AARCH64_OP_SME operands, for which the plugin operand ABI has no
# representation (there is one register slot per operand and an SME operand
# names a tile, a slice-select GPR and an immediate index).  Every SME
# instruction therefore loses its accumulator dependency.  The tracer does
# not target SME workloads and QEMU's SME support is itself partial.
# Closing this needs an operand-ABI extension, not a boundary fix.
# (was a class-wide rule; narrowed to explicit signatures so a NEW
#  unmodelled operand type on AArch64 still fails the gate)
#  the complementary `R-*-phantom * +za*` form is deliberately absent: the
#  boundary drops SME operands, so a ZA register can only ever be MISSING
#  from its sets, never phantom in them.)

# SVE2.1 / SME2 predicate-as-counter PAIR destinations: `whilege
# { p14.b, p15.b }, ...` writes two predicate registers and Capstone reports
# only the first.  Single-predicate WHILE* forms — which is what any SVE
# (as opposed to SME2) workload emits — are correct, and are verified by the
# predicate end-to-end test.  Re-check on a Capstone bump with
# `cstool -d arm64 ff5f2025`.
aarch64 R-wr-missing while* +p#
aarch64 R-wr-missing p*ext* +p#
aarch64 R-wr-missing pext +p#
aarch64 R-rd-missing psel +r#

# RISC-V CSR operands.  Capstone types the CSR-number operand as one the
# boundary cannot map to a register, so a CSR access shows no CSR
# dependency.  The tracer models CSRs only through the specific ones the ISA
# tables name (frm/fflags -> REG_FCSR, vl/vtype -> REG_VCTRL); a general CSR
# index has no generic register id.  Documented in docs/limitations.rst.

# (The two `c*cmsa` entries that used to stand here were not a disagreement
# between the decoders at all.  They said the bank distinction between the
# MSA control registers was inexpressible, but what the tool was actually
# reporting is that it could not tell Capstone's bare control-register
# NUMBER and LLVM's MSA control-register NAME were the same operand.  The
# MIPS normaliser folds LLVM's spelling onto the number now, using the
# register-number column of the MSA specification, and CFCMSA agrees
# outright.  What survives is one real difference, on CTCMSA only, and it
# is listed at the end of this file with the reason it happens.  The FP
# control registers keep their own entries below; only the MSA half of the
# old block was a spelling artifact.)
# (The ten `*c2` coprocessor-register entries that used to open this block
# were an artifact of this tool, not a disagreement.  Its MIPS normaliser
# dropped the coprocessor index by keeping only the LAST digit, so COP2
# register 15 -- LLVM's `COP215` -- read as `cop5` and compared against the
# wrong register for every coprocessor register above 9.  The index comes
# off the front now.  The blind spot that hid it is the same one the sweep
# fill sets exist to close: Rd never took a value large enough to reach a
# two-digit coprocessor register until (31, 0) was added to the MIPS fills.)
mipsel R-rd-missing cfc1 +fcsr
mipsel R-rd-phantom cfc1 +cop#
mipsel R-wr-missing ctc1 +fcsr
mipsel R-wr-phantom ctc1 +cop#

# (MIPS DSP accumulators $ac1..$ac3 on the two-operand MADD/MSUB forms:
# Capstone names only the implicit HI:LO pair.  The tracer's HI:LO chain is
# intact (probe_implicit_acc pins it); the extra DSP accumulators are not.
# Covered by the explicit madd / maddu / msub / msubu entries in section 3;
# the class-wide form that used to live here spelled the family
# `m[as][du][db]*`, which the matcher reads literally and never matched.)

# =====================================================================
# 4. The subtarget gap (class D-cs-only): the boundary decoded it and
#    LLVM did not.
#
#    THIS CLASS IS SPECIAL AND THE TOOL ENFORCES IT.  A `D-cs-only`
#    signature is not one finding among many — it is an encoding on which
#    the register, memory and branch comparisons DO NOT RUN AT ALL, because
#    a rejected LLVM decode short-circuits the compare.  The number of
#    signatures here is therefore the size of this gate's blind spot, and
#    isaxcheck reports it as `subtarget_gap=<signatures>/<encodings>` in
#    its summary line.
#
#    Two rules follow, and isaxcheck refuses an allowlist that breaks the
#    first of them:
#
#      * NO WILDCARDS.  `aarch64 D-cs-only *` was one line, and it hid
#        every extension family a Capstone bump might add.  Each signature
#        is named, or the entry is refused at load time.
#      * A LINE HERE IS THE SECOND-CHOICE FIX.  The first choice is to add
#        the missing feature to kIsaTable so the gap CLOSES.  That is what
#        happened to mipsel (+mips3d) and to the whole of riscv64, which
#        now reports subtarget_gap=0/0 — and closing the RISC-V gap is what
#        made the Zacas `amocas.*` dropped destination visible at all.
#
#    So the only entries below are AArch64's, where `+all` is already the
#    widest subtarget LLVM has and the residue is Capstone accepting
#    encodings the architecture does not define.  See also
#    docs/limitations.rst, "Wrong-path decode of arbitrary bytes".
# =====================================================================

# (a) Architecturally-fixed fields holding reserved values.  `0x88c0e022`
# has Rs != 0b11111 and is therefore not a valid LDAR, but Capstone decodes
# it as `ldar w2, [x1]` while LLVM rejects it.  The same shape covers the
# load/store-exclusive and acquire/release families (Rs and Rt2 must both
# read 0b11111), ADDG/SUBG (op3 must be 0b00) and SB (CRm must be 0b0000).
# On the correct path the bytes never occur.  On the wrong path, where the
# tracer decodes arbitrary bytes, it means a template can describe a
# plausible instruction where the hardware would raise UNDEFINED; the
# tracer's wrong-path fidelity contract already treats wrong-path
# instruction identity as best-effort.
# AXFLAG and XAFLAG join on the same terms from the other side of the
# encoding space: they are MSR-immediate forms whose CRm field the
# architecture fixes at 0b0000, and `0xd500415f` sets CRm = 0b0001.  The
# properly-encoded `0xd500405f` decodes identically on both sides, which is
# how the two were told apart.
# Verify with `cstool -d arm64 22e0c088` on a Capstone bump: if Capstone
# starts rejecting the reserved encodings, every line here goes dead and
# the tool says so.
aarch64 D-cs-only addg
aarch64 D-cs-only axflag
aarch64 D-cs-only ldar
aarch64 D-cs-only ldarb
aarch64 D-cs-only ldarh
aarch64 D-cs-only ldaxr
aarch64 D-cs-only ldaxrb
aarch64 D-cs-only ldaxrh
aarch64 D-cs-only ldlar
aarch64 D-cs-only ldlarb
aarch64 D-cs-only ldlarh
aarch64 D-cs-only ldxr
aarch64 D-cs-only ldxrb
aarch64 D-cs-only ldxrh
aarch64 D-cs-only sb
aarch64 D-cs-only stllr
aarch64 D-cs-only stllrb
aarch64 D-cs-only stllrh
aarch64 D-cs-only stlr
aarch64 D-cs-only stlrb
aarch64 D-cs-only stlrh
aarch64 D-cs-only subg
aarch64 D-cs-only xaflag

# (b) CONSTRAINED UNPREDICTABLE register aliasing on the pair forms.  The
# architecture leaves `ldp w2, w2, [x1], #28` (Rt == Rt2) and
# `stp wzr, w0, [x0], #40` (writeback Rn == Rt2) undefined; LLVM refuses
# them, Capstone decodes them.  This is the same best-effort wrong-path
# space as (a) — the difference is that the fields are legal in isolation
# and only their COMBINATION is not, so no field check would catch it.
aarch64 D-cs-only ldaxp
aarch64 D-cs-only ldnp
aarch64 D-cs-only ldp
aarch64 D-cs-only ldpsw
aarch64 D-cs-only ldxp
aarch64 D-cs-only stgp
aarch64 D-cs-only stp

# The single-register half of the same family, reachable since the sweep
# started filling Rt == Rn (see sweep_aarch64).  A writeback load whose
# transfer register IS its base register — `ldr w0, [x0], #1`,
# `ldr w0, [x0, #0]!`, and the pointer-authenticated `ldraa`/`ldrab` — has
# two definitions of one register and the architecture leaves it
# CONSTRAINED UNPREDICTABLE.  LLVM SoftFails, Capstone decodes; the store
# forms are unconstrained and agree, which is how the boundary of the
# family was located.
aarch64 D-cs-only ldr
aarch64 D-cs-only ldraa
aarch64 D-cs-only ldrab
aarch64 D-cs-only ldrb
aarch64 D-cs-only ldrh
aarch64 D-cs-only ldrsb
aarch64 D-cs-only ldrsh

# (c) THE ONE BELOW IS AN LLVM DEFECT, not a subtarget gap, and it is
# recorded here only because a rejected LLVM decode is what the class
# means.  `ldtr w0, [x0, #1]` is a perfectly well-defined instruction:
# LDTR is the UNPRIVILEGED load, it has no writeback, and the ARM ARM puts
# no constraint on Rt == Rn for it.  LLVM refuses it anyway, because
# AArch64Disassembler.cpp's DecodeSignedLdStInstruction() tests
#
#     bool IsIndexed = fieldFromInstruction(insn, 10, 2) != 0;
#     // Cannot write back to a transfer register (but xzr != sp).
#     if (IsLoad && IsIndexed && !IsFP && Rn != 31 && Rt == Rn)
#       return SoftFail;
#
# and bits [11:10] select the addressing form: 0b01 post-index, 0b11
# pre-index — and 0b10 LDTR, which writes back nothing.  The check's own
# comment says what it is for; the predicate admits one form it was not
# meant to cover.  Fix upstream: exclude 0b10 from IsIndexed.  Capstone
# and the tracer are right, so nothing here needs changing, and these
# lines go dead when LLVM is fixed.
aarch64 D-cs-only ldtr
aarch64 D-cs-only ldtrb
aarch64 D-cs-only ldtrh
aarch64 D-cs-only ldtrsb
aarch64 D-cs-only ldtrsh

#     gap made visible.  These were inside "LLVM rejects this" until the

# RVV whole-register MOVE reports the vector-context CSRs it does not read.
# `vmv2r.v` copies a register GROUP by architecture, independent of vl and
# vtype -- that is the point of the instruction -- and Capstone attaches the
# RVV context reads anyway.  Same family as the vl/vtype phantoms above, and
# reached only once (1, 0) joined the RISC-V sweep fills: the whole-register
# moves need rd = v0 to print their two-operand form.
riscv64 R-rd-phantom vmv2r.v +vl,vtype

riscv64 R-wr-missing cmop.* +r#
riscv64 R-rd-missing *ntl* +r#

# RISC-V hint encodings whose architectural effect is "nothing":
# `c.addi rd, 0`, `c.slli64`, `c.srai64`, `c.srli64` are HINTs.  Capstone
# reports no write (correct for a hint); LLVM reports the nominal write.
# It reports the nominal READ too, and that half the tracer does not keep:
# the dependency model drops it so a HINT arrives as a whole no-op rather
# than as a source with no destination.  That repair is one layer down and
# asserted in isaxcheck_fixups.txt (`riscv64 W-rd-dropped c.addi -*`), so
# the read still agrees HERE — this entry covers only the write.
riscv64 R-wr-missing c.* +r#

# RISC-V JAL/JALR link-register write: the alias-hidden link dataflow is
# recovered inside the plugin by probe_rv_link_dataflow (verified
# end-to-end: `call $0x105cc -> %lr`), which is downstream of the boundary
# this tool measures.  The trace is correct; the boundary alone is not.
riscv64 R-wr-missing jal +r#
riscv64 R-wr-missing jalr +r#
# (`riscv64 R-rd-phantom jalr +r#` used to close this block.  It was the
# same tool artifact the MIPS note in section 1 describes, and on RISC-V the
# erased token `r2` IS the stack pointer: `jalr ra, 0(sp)` lost the one
# register it reads.  LLVM reported it correctly throughout.)

# 5. Explicit residual baseline.
#
# Everything below is one line per observed signature, not a wildcard: a
# NEW disagreement still fails the gate.  These are the signatures that
# survive the fixes and do not fall into a family above.  They have been
# swept into three buckets by inspection, and the bucket is named in the
# comment that precedes each block; what they have in common is that none
# of them is a lost or fabricated dependency on an instruction a compiler
# emits for the ISA subsets the tracer targets.
#
# To regenerate after a Capstone or LLVM bump:
#   build/contrib/plugins/isaxcheck --isa=<isa> --jobs=8 [--mattr=...] \
#       --allow=<this file> --check
# then move any signature that is genuinely new into the right section
# above, or fix it.  Do not regenerate this block wholesale without
# reading the diff — that is how a real regression gets blessed.

# --- aarch64: SIMD structure / SVE gather register-set shape differences,
#     SVE2.1-only forms, and the load/store-multiple writeback tuple naming.
#     Each was inspected: the register is present on both sides under a
#     different tuple spelling, or belongs to a feature above.
# Exception generation.  Capstone puts BRK / HLT / SVC / HVC / SMC in a
# control group and LLVM's MCInstrDesc gives them none — it describes them
# as ordinary instructions with an immediate, because a trap's edge is not
# one a compiler's CFG follows.  The tracer needs the edge: a trap ends a
# true BB.  `svc` and `smc` are here rather than only `hvc` because the
# sweep now fills Rd = 1 and Rd = 3, which is what selects them (see
# sweep_aarch64); the classification they get is asserted in
# isaxcheck_fixups.txt, which is the file that would notice it regressing.
aarch64 B-flow-presence hvc cs-yes llvm-no
aarch64 B-flow-presence smc cs-yes llvm-no
aarch64 B-flow-presence svc cs-yes llvm-no
aarch64 M-cs-mem-llvm-none dc
aarch64 M-cs-mem-llvm-none ld64b
aarch64 M-cs-mem-llvm-none ldapursb
aarch64 M-cs-mem-llvm-none ldapursh
aarch64 M-cs-mem-llvm-none ldapursw
aarch64 M-cs-mem-llvm-none prfm
aarch64 M-cs-mem-llvm-none prfum
aarch64 M-cs-mem-llvm-none rprfm
aarch64 M-cs-mem-llvm-none st64b
aarch64 M-cs-mem-llvm-none st64bv
aarch64 M-cs-mem-llvm-none st64bv0
aarch64 M-cs-mem-llvm-none stgm
aarch64 M-cs-mem-llvm-none stzgm
# mayLoad / mayStore are LLVM SCHEDULING properties, not semantics: they
# say "do not move memory across me", which is precisely what a barrier is
# for, and LLVM sets both on the whole barrier and hint space to get that

# THE AArch64 LOAD-EXCLUSIVES, and the reason they only became visible at
# 733a65dfb0.  LLVM sets mayStore on ldxr / ldaxr / ldxp / ldaxp (with the
# byte and halfword forms) the same way it sets it on the barriers above:
# the exclusive monitor is unmodelled state, and mayStore is how the
# scheduler is told not to move memory across it.  Architecturally a
# load-exclusive reads memory and marks the monitor; it writes nothing.
#
# Until 733a65dfb0 nothing appeared here, and that was two errors
# cancelling rather than agreement: Capstone 6.0.0-Alpha7 reports
# READ|WRITE on the MEM operand of these forms, so the boundary claimed a
# store too and the comparison matched.  The Capstone side is now
# corrected (cap_aarch64_exclusive_mem_access), and the disagreement it
# leaves is LLVM's alone.
#

# ldaxr entry declared `st[%gp1]` with no address and every execution
# delivered only `ld=`, never `st=` -- a slot QEMU's memop callbacks can
# never fill.  ldar is the control (READ only, unchanged) and the LSE
# read-modify-writes (ldadd, swp) keep both slots, so this is specific to
# the exclusives rather than a blanket rule about acquire/release.

# --- x86_64 baseline.
#
# x86 is swept for REGRESSION detection only, and its residual is recorded
# here wholesale rather than triaged signature by signature.  The reason is
# that x86 already has an independent, DYNAMIC ground truth that this static
# check cannot match: the Intel PIN pairing, which found the five defects the
# existing disas/capstone.c x86 workarounds address and which remains the
# authority for effective addresses, real access sizes, rep fan-out and
# segment interactions.  Against LLVM MC the x86 residual is dominated by
# systematic modelling differences that describe no defect — `bnd` versus
# `repne` prefix printing, LLVM's shadow-stack and flag-modelling
# artifacts, and AT&T operand-order effects.  A fourth used to be listed
# here, prefix-consumption disagreements (Capstone folds `64 65` into one
# instruction, LLVM stops at `gs`); those encodings are no longer scored
# at all — see the size_gap paragraph at the end of this comment.  A handful of entries here ARE candidate defects worth their own
# arc (`adox` losing its destination read, `bswapw`, `cmpxchg8b`/`16b`
# losing mayStore, `cldemote`); they are tracked as x86 work, not as part of
# the non-x86 decode-metadata arc this gate was built for.
#
# "RECORDED WHOLESALE" IS WHAT MAKES THIS BLOCK DANGEROUS, and two of its
# rows have already had to be pulled back out of it.  `M-extra-load` and
# `M-miss-store` on fisttpl, fisttpll and fisttps sat here as residual and
# were a Capstone access-flag defect -- the truncating x87 integer stores
# reported as loads -- now repaired at the boundary
# (cap_x86_x87_mem_access in disas/capstone.c) and deleted.  A wholesale
# block cannot be read as evidence that its members were examined; the
# only rows in it that HAVE been examined are the ones this comment names.
#
# `M-extra-load movq` and `M-miss-store movq` stay, with the justification
# they actually have.  Their sample is `f3480f7e00`, where Capstone says
# `movq (%rax), %xmm0` and LLVM says `movq %mm0, (%rax)`: the two decoders
# have decoded DIFFERENT INSTRUCTIONS from one byte string.  F3 0F 7E is
# MOVQ xmm1, xmm2/m64 and REX.W is ignored on it; LLVM lets the REX.W pick
# the MMX form 0F 7E and drops the mandatory F3.  GNU binutils reads it
# Capstone's way (`rex.W movq (%rax),%xmm0`), so it is two-to-one against
# LLVM and there is nothing at this boundary to repair.  Not the same
# thing as the x87 rows that used to sit beside them, despite the
# identical signature shape.
#
# THE BLOCK LOST 1,668 ROWS AT #169, and the two reasons are not the same
# reason.  1,501 of them named an encoding the comparison NO LONGER RUNS:
# where the two decoders consume a different number of bytes they have
# decoded different instructions, and scoring a five-byte `xrelease xchg`
# against LLVM's one-byte `xrelease` produced a register difference that
# only the length gap created.  isaxcheck now stops before the M/B/R
# classes there and counts the encodings instead (`size_gap=` in the
# summary line; class D still reports the length disagreement itself, and
# gates it here).  So the residual did not get better by 1,501 rows -- the
# question those rows answered was withdrawn, and `size_gap=358/6430995`
# is the standing statement of how much of the sweep that is.
#
# The other 167 rows DID stop disagreeing: `cap_x86_is_cmov` gave CMOVcc
# back the destination read Capstone reports it without (104 rows) and
# corrected FCMOVcc's exchanged operand roles (24), `%riz` / `%eiz` are
# now dropped as the not-a-register LLVM index pseudo they are (105 rows
# across both layers), and `st(1)` / `st1` are one token so the x87
# register operands are compared rather than passed over (33).
#
# What this block still buys: a Capstone bump that changes ANY x86 signature
# shows up as a gate failure rather than as silent trace corruption.

# (b) The two decoders cut a prefix-heavy byte string into different
# instructions.  With ModRM.reg swept, the tails reach byte strings where
# LLVM stops after consuming a prefix as a standalone instruction --
# `llvm{rep}`, `llvm{repne}` -- while Capstone consumes the whole thing.
# The register and memory sets then describe two different instructions, so
# the difference is a length disagreement wearing a metadata disagreement's
# clothes.  This is the family that already dominates the x86 residual;
# the wider sweep reaches more of it, not a new kind of it.
#
# THE TEST FOR MEMBERSHIP IS THE SAMPLE ENCODING, NOT THE SHAPE OF THE
# SIGNATURE, and it was applied to every row below one at a time: the tool
# prints `cs{...}  llvm{...}` beside each bucket, and a member of this
# family has an LLVM side that is a bare prefix (`es`, `gs`, `lock`,
# `repne`, `data16`, `rex64`) or `<cs-reject>`.  A row whose two sides
# print the SAME instruction is not in this family whatever it looks like,
# and eleven such rows were standing on this justification.
#
# Ten of them were x87 -- `M-extra-load` and `M-miss-store` on fnstcw,
# fsts, fstps, fstl and fstpl, every one sampled as
# `cs{fnstcw (%rbx, %rcx)} llvm{fnstcw (%rbx,%rcx)}`, the two decoders
# naming one instruction and disagreeing about which way its memory
# operand points.  That was a Capstone access-flag defect, is repaired at
# the boundary now (cap_x86_x87_mem_access in disas/capstone.c), and the
# ten rows are deleted.  The rest are recorded here with what they
# actually are.  They are NOT prefix-length disagreements and must not be
# re-justified as such:

# 7. The control state the boundary started reporting, that LLVM does
#    not describe.
#
#    Three repairs landed after this file was last derived -- the AArch64
#    system-register operand, the RISC-V CSR operand, and the FPCR/NZCV
#    implicit reads -- and they moved the disagreement to the other side.
#    Where the boundary used to drop a register and LLVM named it, the
#    boundary now names state LLVM's MCInstrDesc carries no implicit use
#    for at all.  A `phantom` verdict in this section does NOT mean the
#    tracer invented a dependency: it means the second decoder has no
#    description of that state, the same way it has none for x86 MXCSR
#    (section 1).  Where the two disagree about architectural fact rather
#    than about modelling, the instrument that decides is the
#    implicit-operand table, whose ground truth is the Arm MRA and the
#    Sail model rather than a decoder -- and it now scores these rows OK.
#
#    The system-register TOKEN in these keys is the class the dependency
#    model records (`sys`, `fcsr`, `vctrl`, `vstart`), not the
#    architectural name.  The tracer folds the whole system-register space
#    onto REG_SYS apart from the few it models specifically, so a token per
#    architectural register would key a separate signature for each -- 11445
#    of them on RISC-V, one allowlist line per CSR number.  WHICH system
#    register an instruction touches is a real question and it is the
#    implicit table's, which names each one exactly.
# =====================================================================

# AArch64 FPCR and FPSR, the two halves of the FP control and status
# word, which LLVM MC models neither of.
#
# The boundary states both directions -- cap_aarch64_fp_status_contract()
# in disas/capstone.c, adjudicated against the Arm MRA
# ISA_A64_xml_A_profile-2022-12 execute pseudocode with QEMU's own
# translator as the second reading.  FPCR is the FP datapath's INPUT
# (rounding mode, FZ, DN, FEAT_AFP's AH/NEP/FIZ, FEAT_EBF16's EBF);
# FPSR is its OUTPUT (the cumulative exception bits IXC/IOC/OFC/UFC/IDC
# and the Advanced SIMD saturation bit QC).  Capstone has a register id
# for FPCR and none at all for FPSR, so both halves ride the FPCR id and
# reach the same generic register, REG_FCSR.

# write.  A mnemonic in one list and not the other is the contract

# their vector and SVE forms) read nothing, and the BF16 dot-product and
# matrix family and the SME array accumulate forms read FPCR without
# writing FPSR.
#

# boundary, having adjudicated it away, does not:
#   sqdmulh / sqrdmulh +fpcr  integer saturating arithmetic reads no

#                             (eretaa.xml)

# the same MRS/MSR pair once the sweep covered the sysreg selector in [9:5]
# (see sweep_aarch64).  LLVM's MRS/MSR descriptions carry the system
# register as an IMMEDIATE — the 15-bit encoding, unexpanded — so there is
# no register operand on that side for any member of this family; the
# section header above says what a `phantom` verdict means here.
#
# REG_TLS is TPIDR_EL0, and `mrs xN, tpidr_el0` is how every thread-local
# access on AArch64 begins, so this is the member with real dynamic weight.

# 7. The x86 ModRM.rm space, reached once rm was swept as well as reg.
#
#    ModRM has two register fields and both of them carry opcode.  Sweeping
#    reg (block 6 above) left rm pinned -- to %rcx on the register tail, and
#    to whichever addressing form each memory tail happened to spell.  Three
#    things sat outside the sweep because of it: the other seven register
#    choices at mod = 11, the mod = 11 opcode-extension columns where rm IS
#    the instruction (`0f 01`, `0f ae`, `0f c7`, the x87 escapes), and the
#    base-register addressing forms at mod != 11.
#
#    That was not a hypothetical gap.  `callq *%rcx` was inside the swept
#    space and `callq *%rdx` was not, and it was the second one that exposed
#    a boundary defect deleting a real architectural read from every indirect
#    call -- a defect twelve entries in this file had grown justifications
#    around.  A pinned field is not a smaller sweep, it is an unmeasured one.
#
#    Sweeping rm multiplies the x86 population by eight, 245,760 -> 1,966,080
#    encodings, and moves the share of a traced x86 population lying inside
#    the swept space from 53.8% to 62.8% of distinct encodings and from 33.6%
#    to 58.8% by dynamic weight.  757 signatures follow.  Two of them are
#    real Capstone defects and are labelled as such -- (h) and (i) -- and one
#    more, (c3), is a decode-table gap that could reach a trace.  The rest is
#    the prefix-cutting artifact that already dominates x86 here, arriving in
#    bulk because the wider sweep puts more opcodes behind the same prefixes.
# =====================================================================

# (e) x87 control and status words, and the implicit stack top.  LLVM
# attaches FPCW as a use and FPSW as a def to essentially the whole x87
# space, because rounding and precision control are inputs to every
# arithmetic result and the status word carries the condition codes;
# Capstone reports the stack registers the instruction names and neither
# control word.  The same difference is already listed for the x87 members
# the ModRM.reg sweep reached (`faddl +fpcw`, `fnstsw +fpsw`); sweeping rm
# reaches the mod = 11 column of the escape opcodes, which is the register-
# to-register half of the same space.  FTST and FXAM are the two where the
# arrow points the other way -- Capstone names the ST(0) read those two
# genuinely perform and LLVM does not.
#
# THE mod = 11 REGISTER FORMS ARRIVED LATE, and not because anything moved:
# until the fields-layer work of #169 the tool spelled Capstone's `st(1)`
# and LLVM's `st1` as different tokens, so every x87 register operand was
# an unmapped name and the register sets were never compared at all.  One
# spelling (norm_x86) made the comparison happen, and this is what it
# found -- which is the whole argument for folding a spelling rather than
# allowlisting it: the rows were always true, they were just unreadable.
#
# The FCMOVcc rows read against a CORRECTED boundary.  Capstone reports
# that family with its two operand roles exchanged -- ST(0) read, ST(i)
# written, for an instruction that moves ST(i) into ST(0) -- and
# cap_x86_is_cmov in disas/capstone.c now forces the destination
# read-write and the source read.  What is left is LLVM's side: its
# description names neither the implicit ST(0) read nor the ST(0) write,
# so the tracer is the one that is right in both directions.
#
# ONE ROW HERE IS A DEFECT, NOT A DIFFERENCE, and is recorded as one:
# `R-wr-phantom fxam +st#`.  Capstone's implicit regs_write for FXAM
# (`--hex=d9e5`) contains ST(0), and the SDM is explicit that FXAM only
# classifies the value in ST(0) and sets C0/C2/C3 -- it does not modify
# it.  The trace therefore carries a definition of ST(0) that never
# happened, a WAW edge against whatever wrote it last.  Left uncorrected
# deliberately: it is one instruction, essentially absent from compiled
# code (x87 classify), and the boundary already carries as many
# hand-written corrections as it should before the execution-derived
# capture replaces the source of all of them.  Named so it cannot be read
# as vouched for; owed upstream with the CMOV/FCMOV report.

# (h) A REAL CAPSTONE LENGTH DEFECT, recorded as one rather than as a
# modelling difference.  `66 48 c2 11 22` is `data16 rex.W ret $0x2211`, five
# bytes.  LLVM 18.1.3 says five and GNU binutils 2.42 says five; Capstone
# 6.0.0-Alpha7 says SEVEN while printing the correct 16-bit immediate, so its
# length accounting and its printer disagree with each other.  `RET imm16`
# takes a fixed 16-bit immediate whatever the operand size, so there is no
# reading of the encoding under which seven is right.  The trigger is
# specifically `66` followed by REX.W: `--hex=66c2112233` is 4 (correct),
# `--hex=663ec2112233` is 5 (correct), `--hex=48c2112233` is 4 (correct),
# `--hex=6648c211223344` is 7 (wrong).  It is the same defect already
# recorded above for `66`-prefixed JMP rel, where Capstone consumes a rel32
# where the operand-size prefix selects rel16 (`--hex=663ee911223344`).
# The tracer does not take instruction boundaries from Capstone -- QEMU's
# translator owns those -- so this corrupts disassembly text, not the trace.
# Not filed upstream, by maintainer decision; the line goes dead on a
# Capstone bump and the gate turns red.
x86_64 D-size-mismatch retw

# (i) A REAL CAPSTONE MISIDENTIFICATION, and the reason this signature is
# NOT filed under (g) even though its class looks identical.  `f3 0f 01 ee`
# is CLUI and `f3 0f 01 ef` is STUI -- LLVM 18.1.3 and GNU binutils 2.42 both
# say so -- but Capstone 6.0.0-Alpha7 names them `rdpkru` and `wrpkru`, the
# unprefixed forms at the same ModRM byte.  It consumes the F3 (it reports
# size 4) and then does not dispatch on it, while handling F3 correctly two
# columns over at `f3 0f 01 ea` SAVEPREVSSP and `f3 0f 01 e8` SETSSBSY.  The
# consequence for a trace is not cosmetic: RDPKRU writes EAX and EDX and
# reads ECX, CLUI touches no general-purpose register at all, so a CLUI would
# be recorded with three register edges it does not have.  The signature
# lands in the memory class only because LLVM's CLUI carries the barrier
# mayLoad/mayStore of (g) and Capstone's RDPKRU does not -- the class is an
# accident of which instruction each side thinks it is looking at.
# Reproduce with `--hex=f30f01ee` and `--hex=f30f01ef`.  Not filed upstream,
# by maintainer decision.

# CAUSE 3 (136 entries) -- SEGMENT AND DIRECTION-FLAG MODELLING.  Reached
# because mod = 10 puts a string-op opcode where the ModRM byte goes, so
# a prefix byte in the opcode slot now produces real segment-overridden
# string forms.  Two sub-shapes, both benign, both checked:
#
#   `+seg`: LLVM's X86 memory operand always carries a segment-register
#   slot, so an explicit override makes LLVM report a segment read.  For
#   the overrides here -- ES (`26`), CS, SS and DS (`3e`) -- 64-bit mode
#   forces the segment base to zero and the override contributes nothing
#   to the effective address, so the boundary is right not to record a
#   dependency.  THIS IS NOT THE SAME AS DROPPING FS/GS: those two do
#   have a live base, and the tracer records them.  Verified directly --
#   `--hex=64488b042500000000` (`movq %fs:0, %rax`) gives boundary
#   RD{seg}, LLVM RD{seg} and fields SRC{REG_SEG3}, and the `%gs:` form
#   gives REG_SEG4.  The benign family and the family that would have
#   been a real defect are distinguishable, and only the benign one is
#   here.
#
#   `+df` USED TO BE THE SECOND SUB-SHAPE, and it was a gate blind spot
#   rather than a difference.  LLVM reports the direction flag as a read
#   on the string ops, the boundary reports the whole flags word, and
#   `norm_x86()` folded neither onto the other -- so the two tokens stood
#   opposite each other permanently, could not cancel, and could not
#   fail.  The normaliser now folds `df` onto `flags`, which is what the
#   tracer itself does (both land in the one REG_FLAGS slot), so every
#   `+df` qualifier in this block is gone: what is left is either the
#   residual that was standing behind it, respelled in place, or nothing
#   at all.  The DIRECTION FLAG section at the end of this file carries
#   the measurement.

#

#   the fix ADDED, and they describe no defect.  LLVM marks the masked

# --- x86_64: the residual left once the DIRECTION FLAG became comparable.
#
# LLVM models DF as a register in its own right; Capstone models it as a bit
# of EFLAGS and names the whole word.  `norm_x86()` used to leave the two
# apart, and a token only one side can ever produce is not a comparison.
# Every string instruction carried a permanent `R-rd-missing <mnem> +df`
# beside a permanent `R-rd-phantom <mnem> +flags`, the pair could not cancel,
# and -- the part that made it a blind spot rather than noise -- the boundary
# could have LOST its flags read outright without moving either signature,
# because `df` would still have been the LLVM-only token and `flags`
# vanishing from the Capstone side is not what the phantom bucket is keyed
# on.  A defect in the one register every string instruction depends on was
# structurally invisible.
#
# `df` is now folded onto `flags`, which is what the tracer itself does (both
# land in the single REG_FLAGS slot), so the two sides meet.  Verify with
# `--hex=f3aa` (`rep stosb`): boundary RD{flags,r0,r1,r7} against LLVM
# RD{flags,r0,r7} -- the flags read cancels and only the REP counter is left
# over.  A lost flags read on a string instruction now surfaces as
# `R-rd-missing <mnem> +flags`, which nothing here allows.
#
# The fold retired 328 entries.  205 came back with the same class and
# mnemonic and `df` gone from the qualifier; those were edited in place, in
# the blocks that already justified them, so this section does not hold
# them.  123 were removed, and 80 of those are class/mnemonic pairs with no
# surviving signature at all -- the disagreement they recorded has ceased to
# exist, which is the measurement that says the fold closed something rather
# than renaming it.
#
# What follows is the residual those entries were standing in front of: two
# families already documented above, now visible without `df` in the way.
#
# (a) THE REP COUNTER.  Capstone reports %rCX as read and written by every

# SIB.index and SIB.base were the last large pin in the x86 sweep.  The SIB
# byte used to be whatever the tail happened to spell -- `8d` on the SIB

# index x base is now enumerated in

# =====================================================================
# mipsel -- the CP0 registers a system-control instruction OWNS
# =====================================================================
#
# WHAT: the boundary reports a CP0 register on the TLB and CP0-control
# instructions; LLVM reports none.
#
# WHY IT IS NOT A TRACER DEFECT: CP0 access is the entire architectural
# effect of these instructions, and QEMU's helpers name the registers one
# at a time -- r4k_helper_tlbr writes EntryHi/EntryLo0/EntryLo1/PageMask
# and reads Index (target/mips/tcg/system/tlb_helper.c:240),
# exception_return reads Status/EPC/ErrorEPC and clears EXL,
# helper_dvpe/evpe read-modify-write MVPControl.  LLVM's MIPS descriptors
# carry no implicit CP0 list at all.  This is NOT the footprint of an
# exception: the trap forms (syscall / break / sdbbp / t*) are
# deliberately absent, because by that rule every load that can miss the
# TLB would name CP0 too.  The tracer folds every CP0 register onto one
# REG_SYS bucket, so the CP0 number chosen at the boundary describes the
# access rather than being individually resolvable.
#
# HOW TO DELETE: if LLVM MC grows implicit CP0 lists for these the
# signatures stop appearing and the dead-rule arm fails.  Spot-check with
# `--hex=02000042` (`tlbwi`) and `--hex=18000042` (`eret`).
mipsel R-rd-phantom deret +cop#
mipsel R-wr-phantom deret +cop#
mipsel R-rd-phantom dvpe +cop#
mipsel R-wr-phantom dvpe +cop#
mipsel R-rd-phantom eret +cop#
mipsel R-wr-phantom eret +cop#
mipsel R-rd-phantom evpe +cop#
mipsel R-wr-phantom evpe +cop#
mipsel R-rd-phantom tlbinv +cop#
mipsel R-rd-phantom tlbinvf +cop#

# =====================================================================
# mipsel -- the MT ASE far operand's register FILE
# =====================================================================
#
# WHAT: on MFTR / MTTR the boundary reports the far operand in the file
# the (u, sel) pair selects -- CP0, DSP accumulator, DSPControl, FPR, FP
# control or COP2 -- where LLVM reports a GPR.  Hence the paired
# `+cop#`/`+ac#`/`+dsp`/`+f#` phantom and the `+r#` missing on the same
# encoding: one operand reclassified, not two disagreements.
#
# WHY IT IS NOT A TRACER DEFECT: the far operand is not a GPR, and
# reporting it as one both fabricates a dependency on a register the
# instruction never touches and deletes the one it does.  QEMU's gen_mftr
# / gen_mttr switch on exactly this pair (target/mips/tcg/translate.c:8077
# and :8301); binutils' mips-opc.c is the only static reference that names
# the file per form.  mftgpr / mttgpr (u=1, sel=0) genuinely ARE
# GPR-to-GPR, agree with LLVM, and are absent here -- the family is not
# corrected wholesale.
#
# HOW TO DELETE: if LLVM models the MFTR/MTTR operand classes these stop
# appearing.  Spot-check with `--hex=00200541` (`mftc0 $a0, $5`, must read
# a CP0 register) against `--hex=20200541` (`mftgpr`, must still read r5).
mipsel R-rd-missing mftr +r#
mipsel R-rd-phantom mftr +ac#
mipsel R-rd-phantom mftr +cop#
mipsel R-rd-phantom mftr +dsp
mipsel R-rd-phantom mftr +f#
mipsel R-wr-missing mttr +r#
mipsel R-wr-phantom mttr +ac#
mipsel R-wr-phantom mttr +cop#
mipsel R-wr-phantom mttr +f#

# =====================================================================
# mipsel -- the EVA unaligned loads merge into their destination
# =====================================================================
#
# WHAT: the boundary reports $rt as a READ on `lwle` / `lwre`; the sweep's
# LLVM side reports no read because the disassembled MCInst leaves the
# tied operand unmaterialised.
#
# WHY IT IS NOT A TRACER DEFECT: the read is real and LLVM's own
# MCInstrDesc carries TIED_TO for it -- only the MCInst drops it, the same
# shape as the plain LWL/LWR entries.  QEMU makes it literal: `case
# OPC_LWLE:` sets mem_idx and falls straight through into `case OPC_LWL:`,
# whose body opens with gen_load_gpr(t1, rt)
# (target/mips/tcg/translate.c:2128).  A partial write that keeps the rest
# of the register is a read-modify-write.
#
# HOW TO DELETE: if Capstone or LLVM materialises the tie, re-check with
# `--hex=1900a47c` / `--hex=1a00a47c`.
mipsel R-rd-phantom lwle +r#
mipsel R-rd-phantom lwre +r#
